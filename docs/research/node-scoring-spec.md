# 节点打分系统设计规范（node scoring spec）

> 任务：先有「分」，再谈节点页版面。本文是**设计规范 + 生产数据回算**，不含生产代码改动。
> 数据源：生产 `call_log.jsonl`（**233,692 行**，2026-08-13 → 2026-10-20）、`proxy_state.json`（219 节点状态）。
> 回算脚本与原始输出：`.research/scoring/`。状态：**§0–§5 已定稿**；§4 为生产数据回算结果，§5 为前端字段契约。

## §0 一句话结论

**用一个 0–100 的「可信可用分」= 60% 真实调用质量下界（按失败类型加权 + 7 天半衰期 + 小样本收缩）+ 20% 探测健康分 + 20% 延迟分，再用探测/冷却状态做硬性封顶；分档 优/良/观察/停用，每个分档必须能列出扣分原因（reasons）；分数直接作为未来自动选节点的权重，并用「低样本探索配额」抵消负载自我强化。**

---

## §1 打分目标（为谁服务）

### 1.1 三个使用者，三种用途

| 使用者 | 用途 | 对分数的要求 |
|---|---|---|
| **人（面板）** | 排序 + 解释：「最差的前 10 个」一眼看到，且能看懂为什么 | 分档一眼可读、每档附 `reasons[]`、能区分「质量差」与「冷却中」 |
| **运维/排障** | 判断「该不该切、切完有没有变好」 | 时间衰减 + `last_success_at` + `sample_size`，避免拿旧证据冤枉节点 |
| **未来的自动选节点** | 当选择权重 | 连续、可比较、对样本量稳健、不被流量分布自我强化 |

### 1.2 明确**不做**的事

1. **不做「内卷式排名」**：不显示「第 3 名 / 共 219」这类名次，不给节点贴「优秀节点」荣誉。分数只回答一个问题：**这个节点现在该不该继续接流量 / 该切走谁**。
2. **不做「节点互相比烂」的惩罚**：一个节点分低，不能因为别的节点分高而进一步扣分（分数是绝对量，不是相对名次）。
3. **不追求「单一综合分」吞掉所有信息**：分只是入口，必须同时给 `reasons[]`（为什么扣分）与 `usable`（现在能不能用）两个正交信号；额度冷却 ≠ 质量差。
4. **不用分数做「永久拉黑」**：分数会随 7 天半衰期回升；只要探测恢复且真实调用恢复，节点应自动回到可用档（见 §3.2）。

### 1.3 成功判据（验收这个设计是否成立）

- 面板默认按 `score` 升序时，**最差 10 个**里 ≥8 个是「真的该切」的（探测判死 / 真实高失败 / 长冷却）；
- 每个 <50 分的节点都能给出 ≥1 条人话原因，且原因与数据对得上；
- 与现有 `state`（available/dead）的一致率 ≥80%，**不一致的每一个都能解释谁更对**（§4.4）；
- 分数能直接映射成选择权重（`weight=score/100` 或 `score²`），且低样本节点有探索补偿而不是被饿死。

## §2 输入源（只用现有可得数据）

> 三类输入，时效差两个数量级，**不能混算**（§3.3）：真实调用管「天级质量」、探测管「分钟级通不通」、冷却状态管「现在能不能接流量」。

### 2.1 三类输入一览

| 输入 | 载体 | 时效 | 覆盖度 | 决定什么 |
|---|---|---|---|---|
| **真实调用** | `call_log.jsonl` 233,692 行（08-13→10-20，62 天有数据） | 天级（半衰期 7 天） | 95.2% 请求带 `nodes[]`（222,521/233,692）→ 归因出 **238,796 次节点尝试** | `quality`（60%） |
| **探测** | 运行日志，15 分钟一轮 `GET /zen/v1/models` | 分钟级（15 min） | 219/219 节点有 `last_probe_at`，但**只有最新一次**结果 | `probe`（20%）、硬封顶、`usable` |
| **冷却状态** | `proxy_state.json`（219 节点快照） | 快照，无历史 | `state` 219/219、`last_error` 仅 dead 的 83 个 | `dead×0.30` 封顶、`usable`、`cooldown_until` |
| **延迟** | 探测 `latency_ms`（池中位约 1,959 ms） | 随探测刷新 | 有效 130 / `-1` 83 / 缺字段 6 | `latency`（20%） |

### 2.2 真实调用：哪些字段进分，哪些不进

| 字段 | 参与打分 | 怎么用 | 可信度 / 缺口 |
|---|---|---|---|
| `nodes[]` | ✅ 归因主键 | `nodes[]` 里每个被尝试的节点算一次 attempt（平均 1.07 次/请求） | 95.2% 请求有；剩余 11,171 条直连/池空，无法归因 |
| `events[].type` / `.node` / `.detail` | ✅ 核心证据 | `connect_ok`→成功；`connect_error`→1.0 失败；`upstream_error` 按 `detail` 里的 HTTP 码分流（401/403/410/426→cred 1.0，5xx→0.5，429/freetier→额度不计，400/404→剔除）；`stream_interrupt`→0.5；`switch` 只换节点、不覆盖前一条归因 | 25,566 次成功**无事件**：10 月起 `connect_ok` 不再落盘，只能靠 `status` 兜底；仅 20 次事件缺失且非末节点，无法归因 |
| `status` | ⚠️ 只做兜底 | 仅当 `events` 为空且 `status=ok` 时，把最后一个节点记为成功（25,566 次） | **不能单独用**：`fail` 里混着 429/400/404，直接算会把非节点错记到节点头上（§3.4） |
| `duration_ms` | ❌ 不进分 | 只算 p50/p95/p99，供展示与排障 | p95 是**整条请求含模型生成**的时长，不是节点延迟，不能拿它横比节点 |
| `ttft_ms` | ❌ 不进分 | 只算 `ttft_p50` 供展示 | **只有 40,442/233,692（17.3%）请求带该字段**，覆盖率不足以做延迟分项 |
| `ts` | ✅ 间接 | 指数衰减权重 `w=0.5^(age/7)`；参考时间取末条 `2026-10-20T23:07` | — |
| `node_names[]` | ❌ 只做显示 | 提供 fp→节点名映射（如「飞鸟云::美国02aws」） | 211,793/233,692 行有（90.6%）；**23 个节点无映射，回退指纹前 8 位**，面板需标注 |
| `err_msg` | ❌ | 只在 `context canceled` 兜底剔除（样本中极少） | 自由文本，不做结构化归因 |
| `model`/`path`/`req_id`/`prompt_tokens`/`completion_tokens` | ❌ | 不参与 | 与节点质量无关；token 数是模型侧产物 |

> 一句话：**质量分只由「事件级成败」决定，不由 `status` 决定**；`duration_ms`/`ttft_ms` 是展示字段，不是打分字段。

### 2.3 探测：能证明什么、不能证明什么

- 机制：15 分钟一轮，`GET /zen/v1/models`，**连续失败 2 次判死**（`state=dead` + `cooldown_until`）。
- **能证明**：DNS/TLS/代理链路通 + 密钥能过 models 鉴权，即「分钟级网络与凭据可用性」；顺带给出 `latency_ms`。
- **不能证明**：真实推理可用。探测看不到 403 FreeTierError、429 额度、5xx、流式中断 —— §4.4 的 8 个不一致节点**全部**属于这一类。
- 规模：最近 40 轮每轮探测 130–157 个节点、失败 3–36 个，`verdict` 全为 `trusted`（`probe_health.md`）。
- 缺口：**探测历史未落盘**。只有 `last_probe_at`/`latency_ms`/`last_error` 这一份最新快照，没有「最近 N 轮」序列；`ProbeFailStreak` 只存在内存里，重启即丢（§5 的 `trend[]` 因此标「需后端新增」）。

### 2.4 冷却状态：字段与三个陷阱

| 字段 | 有值率 | 用法 | 陷阱 |
|---|---|---|---|
| `state` | 219/219 | `dead` ⇒ 乘 0.30 封顶 + `usable=false` | 只有 available/dead 两态，没有「观察」这一中间态 |
| `cooldown_until` | 219/219 | 面板「冷却至 HH:MM」 | available 节点是**零值 `0001-01-01T00:00:00Z`** 而非 null；dead 的 `cooldown_until` 全部早于探测参考时间（最晚 10-21 08:04 < 08:27）——**过期但 state 仍 dead**，不能用它判断「正在冷却」，要以 `state` 为准 |
| `last_error` | 83/219（仅 dead） | `probe_dead` 的原因文本 | available 节点没有该字段 |
| `last_probe_at` | 219/219 | 探测新鲜度（>45 min 降权，>135 min 再降） | 只有时间戳，没有结果序列 |
| `latency_ms` | 130 有效 / `-1` 83 / 缺 6 | 延迟分项 | `-1` 必须当「未知」，不能当 0 ms（否则死节点反而拿满分延迟） |
| `last_used_at` | 219/219 但**全为零值** | 未使用 | 字段存在但从未写入，别接 |

### 2.5 覆盖度总结（喂给 §4.2）

- 233,692 行 → 222,521 行带节点（95.2%）→ **238,796 次节点尝试**；
- 其中 **236,997 次（99.25%）计入质量分母**；1,059 次额度（0.44%）、720 次剔除（0.30%）、20 次无法归因（0.008%）不计；
- 真实调用覆盖「质量」，探测覆盖「现在通不通」，冷却状态覆盖「能不能接流量」——**三者缺一，面板就会答错问题**；§5 的 `score` / `usable` / `reasons` 三个正交信号正对应这三类输入。

## §3 必须处理的 7 个坑（本文重点）

### 3.1 样本量不均 → **Wilson 95% 下界 + 池内先验**

10 万次 vs 12 次不能直接比成功率。选择 **Wilson score lower bound（单侧 95%，z=1.645）** 作为「质量下界」：
- 天然惩罚小样本：0/1 成功 ⇒ 下界 ≈0；10/12 成功 ⇒ ≈0.55；9000/10000 ⇒ ≈0.89；
- 有界 [0,1]、闭式解、无需额外依赖（比 Beta 分位数更适合落实现）；
- 与「拉普拉斯平滑」相比不需要人工选伪计数；与「贝叶斯后验」相比不依赖先验分布假设。
- **冷启动用池内先验注入**：新节点先按池基线（Beta 伪计数 α0=8, β0=2 ⇒ 先验 0.8，见 §3.6）参与，Wilson 下界自然给出「观察档」，同时 `sample_size<20` 标记 `low_confidence`。

### 3.2 时间衰减 → **指数半衰期 7 天**

- 每条请求证据权重 `w = 0.5^(age_days / 7)`；`s_eff = Σ w·success`、`n_eff = Σ w`；Wilson 用 `(s_eff, n_eff)`。
- **半衰期 7 天**理由：①老节点日均几百次请求，7 天 ≈ 万级样本仍够稳；②「昨天坏今天好」在 3–7 天内回升到与好节点同档（半衰期 7 天 ⇒ 14 天后旧坏证据只剩 25% 权重）；③太长（30 天）会让已修好的节点长期背锅，太短（1 天）会让分数抖动、且夜间低流量时段样本不足。
- **快信号单独走探测**（15 分钟一轮、连续失败 2 次判死）：探测负责「分钟级可用性」，真实调用负责「天级质量」，两者不混在一个衰减里（§3.3）。

### 3.3 探测 vs 真实请求冲突 → **各管一段，探测可封顶不可抬分**

- 探测（`GET /zen/v1/models`）只证明「网络通 + 密钥能过 models 接口」，**比真实推理宽松**：它看不到 403 FreeTierError、429 额度、5xx。
- 规则：
  1. **质量分只由真实调用决定**；探测分不参与抬高质量（避免「探测好但推理一直失败」被洗白）。
  2. **探测只做封顶（cap）**：连续失败 ≥2 轮 ⇒ `score = min(score, 30)`（停用档）+ reason `probe_dead`；连续失败 1 轮 ⇒ `cap 60`（观察档）+ reason `probe_unstable`。
  3. 真实样本不足（`n_eff<20`）时，探测成功率作为**先验**进入 Wilson（§3.1/§3.6），此时探测可以抬分——因为此时没有更好的证据。
  4. **冲突显式暴露**：`score_reasons[]` 里同时给 `real_traffic_good` 与 `probe_dead`，面板直接显示矛盾，而不是让分数含糊。真实证据 > 探测证据的优先级写死在规则 2/3 里。

### 3.4 失败类型必须分权重（不能一律算失败）

按「是不是节点的错」分四类（回算用事件级归因，见 §4.2）：

| 类别 | 事件/错误 | 对分数的作用 | 理由 |
|---|---|---|---|
| **节点坏** | `connect_error`、连接超时、TLS 失败、`http 403 FreeTierError`、`401/410/426`（凭据失效/被拒） | **权重 1.0 的失败** | 换节点就能好，是「该切」的核心信号 |
| **上游抖** | `http 5xx`（500/502/503/529/520） | **权重 0.5 的失败** | 节点通、上游抖；切节点不一定有用，降权但仍算扰动 |
| **额度耗尽** | `http 429`、`quota_halt`、`FreeUsageLimitError` | **完全不计入质量分母**；若进入冷却则 `usable=false` + reason `quota_cooldown` | 不是质量差，是「这个节点现在没额度了」；冷却该有，扣质量分不该有 |
| **非节点错** | `context canceled`、客户端断开、`http 400`（请求形态）、`404`（模型不存在、与本节点无关） | **完全剔除** | 记到节点头上会造成「用户一取消，节点分变差」的假信号 |

> 补充：`stream_interrupt`（178 次）按 0.5 计（疑似上游/网络抖动，不算纯节点坏）。

### 3.5 负载不均的自我强化 → **分数只用「每次尝试」比率，选择权重加探索项**

- 分数公式全部基于**比率与下界**（成功率、p95），**不含「被选中次数」**：被选中多不会自动加分，被选中少不会自动扣分。
- 现有 canary 对照组意味着「哪些节点拿到流量」本身受算法影响 ⇒ 低样本节点可能是「没轮到」而不是「差」：
  - `sample_size<20` ⇒ `low_confidence=true`，面板明确标注「样本不足」；
  - 自动选节点阶段给 `weight = (score/100)^2 × (1 + 0.5/sqrt(1+n_eff))` 的探索补偿，并保底 5% 流量给低样本节点（canary 扩量），避免「没数据→分低→没流量→更没数据」的死循环。
- 一致性指标里会**单独统计**「分低但样本少」的节点数（§4.4），这类不算真差。

### 3.6 冷启动 → 池内先验 +「观察档」+ 解锁阈值

- 新节点无真实样本：用**池内先验** `α0=8, β0=2`（池基线成功率约 0.8，来自 §4.1 实测），Wilson 下界 ≈ 0.55–0.6 ⇒ 初始落在**观察档**（50–69），不会直接被当「停用」，也不会被当「优」。
- **解锁阈值**（允许接自动流量）：
  - 真实 `n_eff ≥ 20` 且 `score ≥ 70`，或
  - 连续 3 轮探测成功（`probe_ok_streak ≥ 3`）且 `score ≥ 60`（快速通道，给新节点/刚恢复节点）；
  - 未解锁期间：`usable=true` 但 `auto_eligible=false`，只接 canary/手动流量；面板显示「观察中（样本 7/20）」。
- 新节点 `last_success_at` 为空时显示「尚无数据」，不要显示成「0 分」。

### 3.7 量纲 → **0–100 整数 + 四档 + 原因列表**（不是小数，不是名次）

- 对外只给 **0–100 的整数**（内部可保留 1 位小数用于排序稳定性，展示取整）；**永不展示 0.8371**。
- 四档（阈值可由回算微调，语义固定）：

| 档 | 分数 | 含义 | 面板文案 | 颜色（同时配图标/文字，不只靠颜色） |
|---|---|---|---|---|
| **优** | ≥85 | 稳且快，优先给流量 | `可用 · 优` | 绿 + ✔ |
| **良** | 70–84 | 正常，个别抖动 | `可用 · 良` | 蓝/青 + ● |
| **观察** | 50–69 | 有风险信号或样本不足 | `观察 · 谨慎` | 黄 + ⚠ |
| **停用** | <50 | 该切走（坏 / 探测死 / 长冷却） | `该切 · 停用` | 红 + ✕（并显示原因） |

- **正交信号不塞进分数**：`usable`（额度冷却中仍可能是「优」质量）、`low_confidence`、「样本不足」、「冷却至 HH:MM」都独立展示；分数只表达质量+可用性。

### 4.2 归因口径与覆盖率

口径：**一个节点尝试**为分母单位；成败由同请求 `events[]` 中该节点的事件判定；`nodes[]` 中每个节点各算一次。

| 结果 | 次数 | 占尝试 | 计入质量分母 | 说明 |
|---|---|---|---|---|
| 成功 | 204,606 | 85.7% | ✅ | `connect_ok`，或无事件但 `status=ok`（25,566） |
| 失败 | 32,391 | 13.6% | ✅ | 连接失败 / 凭据被拒 / 5xx（半权）/ 流式中断（半权） |
| ↳ 其中半权失败 | 3,172 | 1.3% | ✅（记 0.5） | 上游 5xx + `stream_interrupt` |
| 额度耗尽 | 1,059 | 0.44% | ❌ | 429 / `quota_halt`，不是质量差 |
| 剔除 | 720 | 0.30% | ❌ | 400/404（请求形态）/ 未识别 |
| 无法归因 | 20 | 0.008% | ❌ | 事件缺失且非末节点 |
| **合计** | **238,796** | 100% | **99.25% 可计入** | — |

- 失败类型分布：`connect` 25,528、`cred` 6,839、`http5xx` 3,172、`quota` 1,059（不计）、`confirmed_bad` 24。
- **全局抖动抑制**：失败尝试中 **12,728 次（占 39.3%）** 落在池级抖动窗口（同 10 分钟窗口失败率 ≥50% 且 ≥5 请求），按 20% 计责；另有 3,103 次半权失败同样缩权。不做这一步，10-07/10-18 那种池级故障会把几十个无辜节点一起打进停用档。
- 结论：**99.25% 的节点尝试能进质量分**，剔除率 0.75%，归因口径可用。

### 5.2 排序维度与默认顺序

**默认：`score` 升序（最差在前），但先按 `usable` 分组。**

| 1 | 可用组（`usable=true`，136 个，含 8 个已进停用档的 — 这正是要看的项）在前；不可用组（`state=dead`，83 个）**默认折叠**，只显示计数 | 83 个 dead 会把 8 个真正可操作的项挤到第二屏；折叠后首屏就是行动项 |
| 2 | 组内 `score` **升序** | 页面要回答的是「该切谁」，最低分才是最该看的；§1.2 已明确不做名次，升序不会诱导「比好」 |
| 3 | 同分：`raw_score` 升序 → `sample_size` 降序 → `name` | 避免每次刷新同分节点乱跳（12.4 分那 5 个就是并列） |

| 维度 | 方向 | 空值处理 | 用途 |
|---|---|---|---|
| 分数 `score` | 升序（默认）/ 降序 | — | 找该切 / 找可托付 |
| 成功率下界 `quality` | 升序 | `n_eff=0` 排最后并标「无数据」 | 排除样本量影响看真实质量 |
| 探测延迟 `probe_latency_ms` | 升序 | null 排最后 | 挑快的 |
| 最后成功 `last_success_at` | 降序（最近在前） | null 排**最后**，不要排最前（否则死节点霸榜） | 找「最近真的通过」 |
| 样本量 `n_eff` | 降序 | — | 找证据最充分的 |

### 5.3 呈现建议（能直接落到 UI）

| 元素 | 建议 | 依据 |
|---|---|---|
| **分数** | 大号整数 + 档位胶囊 + 颜色 + 图标（绿✔ / 蓝● / 黄⚠ / 红✕），**永不显示小数** | §3.7；`score` 取整 |
| **原因列表** | 按 `level` 排：`high` → `mid` → `low` → `info` → `good`；**默认显示前 3 条**，其余「展开 N 条」；`good` 类（`real_traffic_good`/`fast`）默认折叠 | 163/219 个节点原因 >3 条，全展开会淹没结论 |
| **样本不足** | 分数旁小徽标「样本 7/20」；`n_eff=0` 显示「尚无真实样本」；**不显示 0 分/0%** | §3.6；29 个节点 `n_eff=0` |
| **无数据（分数=50）** | 6 个 `no_data→观察` 节点分数被人为抬到 50，必须同时显示「未探测到、无真实样本」，否则看起来像「中等」 | `caps: no_data→观察` |
| **矛盾：探测死 / 真实可用** | 档位仍按分数（停用），但原因**并列**显示两条：`探测判死` + `真实调用成功率下界 48%（有效样本 58）`；再加一行「探测不通，但 10-19 还有真实成功」 | 例：`飞鸟云::hy2台湾06` 真实成功率 51.7%、却因 `dead×0.30` 只有 11.4 分 |
| **冷却中** | `state=dead 且 cooldown_until > now` → 「冷却至 HH:MM」；否则「已判死（冷却已过期，待复测）」；零值一律不显示 | §2.4：dead 的 `cooldown_until` 全部已过期 |
| **额度** | 灰标「额度耗尽 N 次」，**不参与红色扣分视觉** | §3.4：额度不是质量差 |
| **延迟** | 显示 `probe_latency_ms`；null → 「—」；不要拿 `p95_ms` 当节点延迟 | p95 含模型生成 |
| **趋势** | 有 `trend[]` 时画 20 格点图（绿/红点，hover 显示延迟与错误）；没有时显示「趋势数据未采集」，**不要画空图** | 0/219 有历史 |

### 5.4 现在就能给 vs 需后端新增

| 能力 | 现状 | 需后端做什么 |
|---|---|---|
| 分数 / 档位 / 原因 / `usable` / `auto_eligible` | ✅ 直接给 | `scores.json` 已是完整契约，取整即可 |
| 样本量 / `low_confidence` / 最后成功 / 最后请求 | ✅ 直接给 | 无需改动 |
| 探测延迟 / 探测时间 / 冷却截止 | ⚠️ 归一后给 | 把 `-1` 与 `0001-01-01T00:00:00Z` 转 null（否则前端会渲染出「延迟 -1 ms」「冷却至 0001 年」） |
| 失败主因 / 失败分类 / 额度次数 | ✅ 直接给 | `fail{}` + `quota_events` |
| `trend[]`（20 轮） | ❌ 无 | **每节点环形缓冲**：`{ts, ok, latency_ms, error}` × 20；219×20 ≈ 4.4k 条（约 350 KB），随 `proxy_state.json` 一起落盘，进程重启不丢 |
| `probe_ok_streak` / `probe_fail_streak` | ❌ 内存中 | 每节点 2 个 int 持久化到 `proxy_state.json`；否则 §3.6 的「连续 3 轮成功快速通道」无法实现 |
| `probe_fail_24h` / `dead_marks_7d` | ⚠️ 靠日志回算 | 接口不能读 72 MB 日志：从环形缓冲推导，或单独落盘计数 |
| `computed_at` | ❌ 无 | 每个分数快照一个时间戳，用于「分数更新于 3 分钟前」 |
| 分数历史（「切完有没有变好」） | ❌ 无 | 每小时快照 ×219 ≈ 5.3k 行/天，保留 7 天（约 37k 行，JSONL 或 SQLite） |

### 5.5 明确**不要**在 UI 上做的

1. **不做名次**：不显示「第 3 名 / 共 219」，不排序号列。
2. **不给荣誉**：没有「优秀节点」「金牌节点」徽章（§1.2）。
3. **不做节点互相比烂**：不显示「比 X 差」「相对分」「击败了 82% 的节点」。
4. **不展示小数分**：不出现 `0.8371`、`37.6`，只给整数。
5. **不把额度冷却画成质量差**：`quota_cooldown` 用灰/蓝，不用红。
6. **不默认铺开 83 个 `dead`**：折叠 + 计数（另有 8 个 available 已进停用档，留在首屏），否则首屏没有行动项。
7. **不用 `p95_ms` 横比节点延迟**：它含模型生成时间。
8. **不给无样本节点显示「0 分 / 0% 成功率」**：显示「尚无数据 / 尚无成功记录」。
