## 0. 结论速览

| 问题 | 结论 |
| --- | --- |
| 现在这页是什么 | **两套东西硬拼在一个 section 里**：①「原始日志」= 应用日志的 SSE 控制台（内存环 5,000 条、接口每次最多 500 条）②「调用日志」= 结构化请求记录（`/api/call-log?limit=500`，5 秒轮询）。**默认着陆在最没人需要的那个**（原始日志）。 |

### 1.3 调用日志的渲染与交互（关键缺陷）

- `loadCallLog()`（`:2219`）→ `fetch('/api/call-log?limit=500')`，**2 秒 AbortController 超时**（`:2226-2228`，注释写明实测 3.17ms / 1.4MB / 22 allocs）。
- `clVisible()`（`:2238`）在**前端**过滤：关键词、日期、只看异常。⇒ 所有筛选都只能在 500 条里挑。
- `clRenderList()`（`:2288`）一行一条：`【成功】/【失败】` + 异常标签 + 时间 + 模型 + 节点链 + 耗时；**只有 `clHasIssue()` 为真的行才有 `onclick`**（`:2295` `(issue?'onclick="clToggle(...)"':'')`）⇒ **成功行点了没反应**（审计实测 493/500）。
- 展开内容（`:2290-2293`）：两行 meta（`req_id / path / stream / route_mode / 错误`、`token / 耗时`）+ 原始事件行（`type` + `node_name||node` + `detail`）。**没有"第几次尝试 / 为什么换 / 最后结论"**，节点名兜底会是 `1::AT-45.39.96.13:5426` 这种指纹串（`clNodeChain()` `:2278` —— 只有在 `node_names` 缺失时才显示指纹）。
- `clRenderHour()`（`:2306`）/ `clRenderNode()`（`:2320`）都是对这 500 条做前端聚合；节点分析里**直连记录被细分成三类**（`:2326-2333`：`直连·闸门拒绝` / `直连·连不上` / `直连·其他`），这是目前唯一"有口径意识"的地方，值得保留。
- 5 秒轮询期间展开态只按 `req_id` 记忆（`callLogExpanded` `:2224`），**滚动位置不保护**（整列表 innerHTML 重建）。

## 2. 后端契约（现状，逐字段）

### 2.1 `GET /api/logs`（应用日志快照）

`logring.go:165` `adminLogsHandler` → 路径分发（`:166-176`）：`/api/logs` / `/api/logs/stream` / `/api/logs/export`，都在 `main.go:7655-7657` 挂了 `requireAuth`。

- **没有任何 query 参数**（读代码确认：`switch r.URL.Path` 后直接 `snapshot(maxLogRows)`）。
- 响应结构 `logsSnapshot`（`logring.go:160-163`）：

```json
{ "entries": [ {"seq":123,"time":"2026-10-20T12:31:07.123+08:00","level":"INFO","msg":"request_started","attrs":[{"k":"request_id","v":"req_9001"}]} ],
  "next_seq": 124 }
```
- `entries` 最多 **`maxLogRows = 500`**（`logring.go:158`），来自内存环 `logRingCapacity = 5000`（`logring.go:15`），环满覆盖（`logring.go:47-58`）。
- **重启即丢**（纯内存）；`/api/logs/export` 最多导出环里 5,000 条（`logring.go:249` 附近 `snapshot(logRingCapacity)`）。

### 2.2 `GET /api/logs/stream`（SSE）

`serveLogStream`（`logring.go:180`）：
- 头：`Content-Type: text/event-stream` / `Cache-Control: no-cache` / `X-Accel-Buffering: no`。
- 首帧推最近 500 条（重连去重靠 `seq`），随后 `globalLogRing.after(last)` 增量；**30 秒心跳**（注释行 `: ping`）。
- 帧格式：`id: <seq>` + `data: <json>`；无 `retry:` 字段（前端自己指数退避 2s→60s，`:2180-2186`）。
- ⚠️ 前端注释记录的坑（`static/admin.html:2174-2179`）：`EventSource` 连接级掉线时**不会进终态**，`onerror` 里必须 `close()`，否则指数自激（实测 128/s→211/s）。

### 2.3 `GET|DELETE /api/call-log`（结构化请求记录，**日志页真正该用的那个**）

`calllog.go:2398` `adminCallLogHandler`：

| 方法 | 参数 | 行为 |
| --- | --- | --- |
| `GET` | **只有 `limit`**（默认 500，`fmt.Sscanf` 解析） | `callLog.latest(limit)` → **反转成最新在前** → JSON 数组 |
| `DELETE` | — | `callLog.clear()` + **同时清零统计**（`tokenStats`，`:2418-2427`）+ `saveTokenStats()` |

- **实测（本轮新构建 `:9071`，文件副本 231,992 行）**：

```
limit=500     → 500 条 / 214,944 B / 1.4 ms / 跨度 2.74 h（16:07:39 → 18:51:58）
limit=2000    → 2000 条 / 844,400 B / 4.6 ms / 跨度 9.66 h（09:12:15 → 18:51:58）
limit=5000    → 2000 条（同上，被环上限钳）
limit=100000  → 2000 条（同上）
?from=2026-08-01&to=2026-08-02&model=big-pickle&limit=50 → 50 条，最新 2026-10-19T18:51:58 ⇒ 这些参数被静默忽略
```
  与审计 §1.3 的结论一致（审计测的是 `2000 条 / 9h39m`），**现状未变**。
- 上限来源有两层：环 `callLogCapacity=2000`（`calllog.go:136`）+ `latest()` 截断；**接口层没有自己的 page 上限**，只是拿不到更多。
- **不读日志文件**。启动时只从文件**尾部倒读 2000 行**回填（`tailReadLastLines` `calllog.go:1346`，调用点 `:1418-1436`，注释明写「只需最后 2000 条，却原本解析了全文件 18.6 万行」）。

## 3. 数据规模与"23 万行怎么查"（本轮最关键的一问）

### 3.1 实测数字（全部本轮复算，命令见 §3.5）

| 指标 | 值 |
| --- | --- |
| 生产文件 | `/data/call_log.jsonl` **233,441 行 / 124,519,173 B（118.8 MiB）**（10-20 12:49）；副本 231,992 行 / 118.0 MiB（10-19 19:48） |
| 时间跨度 | **2026-08-13 → 2026-10-19，61 天** |
| 单行大小 | 平均 **533 B**（118 MiB ÷ 231,992） |
| 全量扫描 + JSON 解析 | **2,029 ms**（231,992 行，114,354 行/秒）⇒ 每次查询都扫全文件**不可接受** |
| 从文件尾倒读 2,000 行 | 读 **1.00 MiB** / **1.7 ms** |
| 倒读 20,000 行 | 读 11.0 MiB / **17.7 ms** |
| 倒读 100,000 行 | 读 50.0 MiB / **82.4 ms** |
| 反向纯字节扫完 118 MiB（不解析） | **14 ms**（页缓存热；为了找到时间边界的最坏下限） |
| 按天若拆成独立文件 | 平均 **1.93 MiB** / 中位 **0.54 MiB** / 最大 **8.77 MiB**（2026-09-30，17,232 条） |
| 读+解析单日最大文件 | **112 ms** |
| 只在全文件里取某一天（无索引） | **2,161 ms** ⇒ 这就是"没有索引的代价" |
| 启动冷启（含尾部 2,000 行回填） | **1,442 ms** |
| 进程内存（RSS / VSZ） | **60.1 MB** / 1,921.6 MB |

### 3.2 三个方案对比

| | 方案 A · 倒序游标（`?before=&limit=`） | 方案 B · 按天分文件 + 索引 | 方案 C · 前端只查最近窗口（现状维持） |
| --- | --- | --- | --- |
| 能查到 61 天历史吗 | ✅ 能（一路往前翻） | ✅ 能（可跳某一天） | ❌ **不能**（最多 2.7h / 接口 9.66h） |
| 单页查询延迟 | 1–20 ms（近端）/ 最坏 ~100–300 ms（翻到最老） | 单日文件 ≤112 ms，可并行 | 1.4 ms（内存环） |
| 磁盘 | 0 额外 | 0 额外（只是把同一份内容重排）+ 索引 ~几十 KB | 0 |
| 内存 | 0 额外（流式倒读，不回填全量） | 0 额外（可按天 LRU 缓存 1–3 天日文件） | 60 MB 常驻（现有环） |
| 实现复杂度 | **小**：复用 `tailReadLastLines`（`calllog.go:1346`）的倒读思路，加过滤/游标即可 | **大**：写入要按天切分 + 存量 118 MiB 一次性迁移 + **统计侧（小时桶回填/everServed）要跟着改读法** | 0 |
| 风险 | 低（纯新增参数，默认行为不变） | **中高**：触碰今天刚上线的统计口径路径（`calllog.go` 小时桶 + `statscan.go` 全量回填） | 0（但功能缺失） |
| 能支持"跳到某天/归档" | ❌（只能顺序往前） | ✅（按天删除/压缩/归档） | ❌ |
| 排序能力 | 只能 `ts` 倒序 | 任意（可按耗时/状态排序，因为单日文件小） | 前端随意（数据已在内存） |

### 3.3 结论

**先 A，后 B；C 不可接受。**

1. **A 就够用**：日志页的浏览模式本质是"往前翻"，用户不会要求"跳到第 837 页"。实测一页 2,000 行只需 1 MiB / 1.7 ms，`before` 游标天然幂等、支持并发打开多个标签页；最坏代价（翻到 8 月）也只是读 118 MiB（页缓存热 14 ms；冷缓存 1–2 s，加个上限/进度提示即可）。
2. **B 是长期优化**，收益是"跳天 / 归档 / 单日并行聚合"，但它必须动写入与统计读取路径，**风险与收益不对等**，应作为独立任务（并且要有"统计数字逐字节不变"的验收门禁）。
3. **C 直接否决**：`unmapped_requests`、失败、被口径剔除的请求"必须在日志页可查"是用户的既有裁决（概览只显示有成功的模型）—— 只查最近窗口等于**永久丢掉历史证据**，61 天里 98% 的数据不可达。

### 3.4 若真要做 B（按天分文件）的成本清单（给 Lead 评估用）

- 写入侧：`appendCallLog` 时判断"当前日期是否变化"→ 关闭旧文件、打开 `call_log/YYYY-MM-DD.jsonl`；需要一个"当前文件句柄 + 当前日期"的原子状态，且**崩溃恢复**要能扫目录找最新文件。
- 迁移：一次性把 118 MiB 按 `ts` 拆 61 个文件（实测全量解析 2 s，可接受）；现有 `/data/call_log.jsonl` 保留为 `legacy.jsonl` 只读。
- 读出侧：`tailReadLastLines` 要变成"按目录定位日文件"；`hydrate` 只读最近 1–2 天；小时桶回填(`statscan.go`) 要能跨全部日文件（或继续读 `legacy.jsonl` + 新目录）。
- 删除/归档：`DELETE /api/call-log` 语义要重新定义（现在是 `clear()` 一个文件）—— 删所有日文件 + 统计清零，必须一次事务（否则会半删）。
- 验收门禁：**同一份数据在 A 方案与 B 方案下，`/api/stats` 的每个数字必须逐字节一致**。

## 6. 三个方向（结构真不同，不是换配色）

> 三个方向共用：**状态带**（范围 + 请求数 + 失败 + 成功率 + 异常数 + 未映射数）、**筛选条**（时间范围 / 状态 / 模型 / 耗时 / 关键词）、**故事线组件**（结论句 + 每次尝试 + 耗时分解 + 原始事件折叠 + 预留路由位）、**详情抽屉**（桌面右侧 / 手机全屏）。差异在**主结构**。

### 6.1 方向① 时间流（终端/聊天式）

- **形态**：粘性筛选条（顶部固定）+ 单列流水，**最新在上**，一页 40 条 + 「加载更多（更早）」；每行一句话摘要，点击就地展开故事线；「实时跟随」开 = 新条目从顶部插入并高亮 1.5s，关 = 冻结位置并显示「有 3 条新记录 · 点此查看」。
- **适合**："刚才发生了什么""现在还在出吗"。
- **不适合**：跨小时/跨天巡检（要一直往下滚）。
- **技术**：`?before=&limit=` 倒序游标（**本版可做，含前端模拟**）；实时增量用 `?after=<ts>` 轮询 5s 或 SSE（**需后端**，本版用模拟）。

### 6.2 方向② 表格 + 详情抽屉

- **形态**：传统表格（列：状态 / 时间 / 模型 / 路径 / 节点数 / 耗时 / 首字 / token / 结果摘要），**分页**（第 N 页 / 共约 M 页，或"上一页/下一页 + 游标"），点任意行 → **右侧滑出抽屉**（列表不动、滚动位置不丢），抽屉里是故事线 + 完整字段 + 原始 JSON。
- **适合**："把最近 200 条按耗时排一下""精确定位某条记录"（信息密度最高）。
- **不适合**：手机（表格必然横向溢出 → ≤640px 自动降级成卡片列表，见 §7.5）。
- **技术**：需要 `?before/from/to/status/model/min_duration_ms&limit` + `has_more`（**需后端**）；排序若要做"按耗时"还需要后端支持或单页内排序（明说限制）。

### 6.3 方向③ 按请求聚合的"故事线"（推荐）

- **形态**：**一条客户端请求 = 一张卡**（不是一行流水）。卡头一句话结论 `mimo-v2.5-free · 试了 3 个节点、换了 2 次 · 最后成功 · 119.4s`；卡内**默认可折叠的尝试时间线**（每次尝试：序号 / 节点 / 结果 / 错误 / 耗时 / 换节点原因）；**耗时分解横条**（建连 / 等首字 / 生成 / 重试空转），一眼回答"为什么等了 2 分钟"；顶部可按「异常优先 / 最慢优先」排序并默认只看异常。
- **为什么它最能排障**：日志里**天然一行就是一个请求**（`CallRecord` 是请求级），多节点尝试都在 `events[]` 里；把它折叠成"一条记录 + 可展开的尝试"正好对应人的问题结构（先结论、后细节），也避免方向②那种"表里看不出重试过"。
- **不适合**：要"扫 200 条原始记录"时比方向①重（卡更高）。
- **技术**：**本版可做**（数据本来就在一条记录里，`nodes[]+events[]` 足够重建故事）；只缺 `attempt_count/outcome/gen_ms/retry_wait_ms` 这类**消歧字段**（没有也能推导，推导规则写在 §7.2）。

### 6.4 4 条排障任务的步数 / 滚屏数（三方向对比，本版预览实测见 §9.3）

| 任务 | ① 时间流 | ② 表格+抽屉 | ③ 聚合故事线 |
| --- | --- | --- | --- |
| T1 找最近一次失败及错误 | 2 步（点「只看异常」→ 看首条已含错误摘要）；0 滚屏 | 2 步（点「失败」筛选 → 首行；错误摘要需看"结果"列）；0 滚屏 | **1–2 步**（默认就是异常优先；卡头一句话直接给结论）；0 滚屏 |

### 6.5 技术可行性（本版可做 vs 需后端改造）

| 能力 | 本版（预览） | 落地需要 |
| --- | --- | --- |

## 7. 五个难点（必须回答，不能含糊）

### 7.1 23 万行历史如何查

见 §3：**方案 A 倒序游标先做**（一页 1 MiB/1.7 ms；最坏 118 MiB/14 ms 页缓存热）；**方案 B 按天分文件后做**（单日 ≤112 ms，可跳天归档）；**方案 C（只查最近窗口）否决**——与"全部请求都能在日志页查到"的裁决冲突。

### 7.2 实时流与历史查询怎么共存（自动滚动会不会打断查看）

三条硬规则（三方向都适用）：

1. **"实时跟随"是一个显式开关，默认开；一旦用户主动滚动/点击任意行/打开抽屉，立刻**自动关闭**并显示「已暂停跟随 · 有 3 条新记录 ↗」的提示条**（点击跳回顶部并恢复跟随）。
2. **历史查询期间（翻了页 / 改了时间范围 / 打开抽屉）实时增量只进"待看队列"，不插进正在看的列表** —— 否则用户正在读第 3 页，第 1 秒就被顶掉。
3. **两条通道分开**：浏览用 `GET ?before=`（历史，倒序、幂等），增量用 `GET ?after=<最新 ts>`（只取比当前更新的，最多 100 条/次）或 SSE；**新记录进列表用"插入到顶部 + 高亮 1.5s"而不是整表重绘**（现状 5s 全量 innerHTML 重绘会把展开态与滚动位置冲掉）。
4. 版本/ID 去重：以 `req_id` 为唯一键（`ts` 可能同毫秒）；`after` 用 `ts` 游标时服务端必须 `ts > after` 严格大于 + 前端按 `req_id` 再过滤一次。

### 7.3 长文本（错误信息、请求体）怎么截断与展开

- 列表/卡头：**单行省略**（`text-overflow:ellipsis`）+ `title` 全文（桌面 hover 可看）。
- 详情：错误信息默认 **3 行**（`-webkit-line-clamp:3`），「展开全文」按钮 + 复制按钮；超过 2,000 字符时才截断并标注「已截断，共 N 字符」。
- 请求体：**日志页不展示**（§2.5：主文件里没有；`log_bodies` 只进应用日志）。若将来要，链接跳「系统日志」并按 `req_id` 过滤 —— 不把 body 塞进主 jsonl（§8.5）。
- 节点指纹串（`1::AT-45.39.96.13:5426`）：**只在 title/原始 JSON 里出现**，可见文本一律显示 `node_names` 兜底「节点 N」。

### 7.4 未映射/失败/超时怎么一眼区分（**不能只靠颜色**）

四重编码，任意一个失效都还能区分：

| 类别 | 文字徽章 | 符号（等宽字体，单色也能认） | 行/卡形状 | 颜色（第 4 位，锦上添花） |
| --- | --- | --- | --- | --- |
| 成功（干净） | `成功` | `✓` | 常规行 | ok 绿 |
| 重试后成功 | `重试成功 · 换 2 次` | `↻` | 行首竖条（虚线） | warn 琥珀 |
| 失败 | `失败 · http 429` | `✕` | 行首竖条（实线，加粗） | danger 红 |
| 超时/中断 | `超时（>60s）` / `流中断` | `⏱` / `⌁` | 行首竖条（点线） | danger 红 |
| **未映射** | `未映射`（灰底、**虚线框**） | `?` | 行首额外 `?` 标记 | 中性灰（**刻意不用红**：它不是失败，是"这名字不归我们管"） |
| 直连（无节点） | `直连` | `→` | 节点列显示「直连」而非空 | 中性 |
| 被闸门挡 | `闸门拒绝` | `⊘` | 行首竖条 | warn |

- 所有徽章都带**文字**，不依赖颜色；`aria-label` 给读屏；筛选 chips 也写文字（「只看异常（含重试成功）」）。
- 未映射**必须可筛**（`unmapped=1`）—— 这是"概览看不到的那批请求"的唯一出口。

### 7.5 手机端（表格必然横向溢出，给替代形态）

- **方向②**：≤640px 时表格**整体降级为卡片列表**（不是横向滚动）：每卡两行（结论 + 元信息），点击 → **全屏 sheet**（底部弹出、`100dvh-56px`、可滚动）而不是右侧抽屉；`overflow-x` 保持 `visible`，**不靠隐藏**。

- **方向③**：卡片单列；尝试时间线竖向（不用横向甘特）；耗时分解条保持横向但只标 2–3 个关键段（建连/首字/生成），其余合并进"其他"。

### 8.0 六条硬要求（逐条回答 Lead）

#### ① 只能追加，不能删或改名既有字段

- 既有 22 个 `CallRecord` 字段（§2.4）+ 4 个 `CallEvent` 字段**一个不动**。
- 历史行（231,992 行里除今天新写的外）没有新键 ⇒ 读取处用 **"键不存在"** 判定，不用零值判定（见 ③）。
- 为什么不能改名：`call_log.jsonl` 被三条已上线路径共读 —— ① `calllog.go` 小时桶回填（`statscan.go` 的 `slimRec` 只认 10 个键）② `everServed` 回填（只读 `model`+`status`）③ `2b` 统计口径。改名会直接让今天刚上的统计失效。

#### ② 兼容策略（具体规则，不写"做兼容处理"）

| 规则 | 内容 |
| --- | --- |
| 写入 | 新字段从实现版本起写入；**新行缺值时不写该键**（Go `omitempty` / 前端不塞 `undefined`） |
| 读老行 | 前端一律 `r.attempt_count === undefined ? derive() : r.attempt_count`（**用键是否存在判断，不用 `0`/`""` 判断**） |
| 显示 | 老行缺失字段显示 **`—`**（不是 `0`），并在详情里给一行小字：「该字段自 2026-10-2x 起记录，这条是更早的记录」 |
| 推导兜底 | `attempt_count` → `max(1, nodes.length)`；`outcome` → `status==='ok' ? 'ok' : 'fail'`；`gen_ms` → `duration_ms - ttft_ms`（ttft 缺失时为 `—`）；`model_in` → 与 `model` 相同并标「未记录原始名」 |
| 不追溯 | **不回填老行**（回填要重写 118 MiB 且会制造"文件在运行中被改写"的窗口；统计不需要这些字段） |

#### ③ 分页/游标的 API 形状（与现有"只 tail 2000 条"如何共处）

**`GET /api/call-log`（同一个端点，向后兼容扩展）**

| 参数 | 类型 | 语义 | 边界 |
| --- | --- | --- | --- |
| `limit` | int | 条数，默认 500 | `1..500`（超过按 500 截断） |
| `before` | RFC3339 或 unix ms | 返回 `ts < before` 的记录（**游标**） | 严格小于；省略=从最新开始 |
| `after` | 同上 | 返回 `ts > after` 的记录，**正序**（用于增量） | 严格大于；与 `before` 互斥（同时给 → 400） |
| `from` / `to` | 同上 | 时间范围，`ts >= from && ts < to`（**左闭右开**，与 `trendBuckets` 口径一致） | 可单给；`to` 省略=不限 |
| `status` | `ok`\|`fail` | 状态过滤 | 非法值 → 400 |
| `model` | string | 模型名精确匹配（对 `model` 字段） | 空=不限 |
| `unmapped` | `0`\|`1` | 只看未映射 | — |
| `min_duration_ms` / `max_duration_ms` | int | 耗时过滤（用于"等超过 60 秒"） | — |
| `q` | string | 关键词，服务端只匹配 `model/err_msg/req_id/path`（**不匹配 events，避免扫爆**） | ≤64 字符 |
| `bucket`/`summary` | — | **不放在这里**，见独立端点 §8.3 | — |

**响应结构（改数组为对象 → 兼容处理见下）**：

```json
{ "records": [ ...CallRecord... ],
  "next_before": "2026-10-19T18:51:58.532+08:00",   // 下一页游标（无更多时为 null）
  "has_more": true,
  "scanned": 2000,                                   // 本次倒读的行数（诊断用）
  "source": "file" }                                 // "ring" | "file"
```

⚠️ **兼容坑**：现在返回的是**裸数组**，前端 `callLogData=recs||[]`。改成对象会打断老前端。两种做法：
- **推荐**：新响应对象，同时**保留**裸数组行为给"无任何新参数"的调用（`source:"ring"` 时仍返回数组）；但这会让前端分支判断变丑。
- **更稳**：加 `?format=2`（或 `Accept: application/vnd.oc2a.v2+json`）返回对象；不带则永远返回裸数组。**前端新代码永远带 `format=2`**，老代码不动。
- 我选后者：**默认行为逐字节不变**（老前端零风险），新参数/新格式靠显式开关。

**与"只 tail 2000 条"共处**：
- **默认（无新参数）走内存环** —— 现状不变（1.4 ms，不读磁盘）；
- **只要出现任一筛选/游标参数** → 走**文件倒读**路径（`source:"file"`），即使结果只覆盖 2 小时也一样；
- 前端策略：默认视图用「最近 1 小时 / 今天」→ 文件路径（因为要 61 天可达）；「实时跟随后台缓冲」用环路径。两个按钮在 UI 上不区分（用户无感），但响应里的 `source` 会写进诊断日志。

#### ④ 不能破坏统计耦合（逐字段点名）

`statscan.go` 的手写解析器（`:117-170`）`switch string(key)` **只认这 10 个键**：`ts / model / status / prompt_tokens / completion_tokens / cache_creation_tokens / cache_read_tokens / ttft_ms / output_speed / duration_ms` + `unmapped`。**其余键一律忽略**（`slimRec` 注释明写"events / nodes / node_names / path / req_id / route_mode / err_msg / stream 从不被统计访问"）。

逐字段确认：下面每个新字段**都不会**被桶聚合/`everServed` 误读。

| 新字段 | 会被 `statscan.go` 读吗 | 会被 `everServed` 读吗（`model`+`status` 之外） | 会被 `models` 聚合误当模型名吗 | 结论 |
| --- | --- | --- | --- | --- |
| `model_in`（string） | ❌ 不在 switch 白名单 | ❌ | ❌（聚合只读 `Model`） | 安全 |

| `outcome`（string） | ❌ | ❌ | ❌（不叫 `status`） | 安全 |
| `gen_ms`（int64） | ❌（不叫 `duration_ms`） | ❌ | ❌ | 安全 |
| `retry_wait_ms`（int64） | ❌ | ❌ | ❌ | 安全 |
| `events[].attempt` / `events[].dur_ms` | ❌（`events` 整个字段都不读） | ❌ | ❌ | 安全 |

补充两条：
- **不许**把新字段命名成 `model_*` / `status_*` / `duration_*` 这类可能被未来通配逻辑吃掉的名字（`routed_from` 而不是 `model_routed_from`）。
- `unmapped` 的判定逻辑**本提案不改**。将来 auto 路由上线要放宽（"逻辑名命中候选组 ⇒ mapped"）是**行为变更**，必须单独立项 + 只对新行生效（老行已冻结 `unmapped` 值，`SawUnmapped` 机制已经能区分，`calllog.go:2135-2160` 那段注释即为此设计）。

#### ⑤ 大字段不进主文件

- **现状已经满足**：`log_bodies` 的 body 摘要只进应用日志（§2.5），主 jsonl 里没有。
- **本提案坚持不加** body 进主文件：一旦加进去，小时桶回填要读的文件会从 118 MiB 膨胀几十倍（单条 body 平均几 KB × 23 万）。
- 若将来要按请求看 body：**单独文件** `call_bodies/YYYY-MM-DD.jsonl`（一行 `{req_id, dir:"req|resp", body:"<截断 4KB>"}`）+ 只按 `req_id` 精确查（倒读找到即停）；保留期 7 天、默认**关**；代价：多一次磁盘随机读（<5 ms）+ 隐私风险（body 里有 prompt），所以要**默认关 + 面板显式开 + 提示"包含用户内容"**。

### 8.3 聚合端点提案

`GET /api/call-log/summary?from&to&bucket=5m|1h|1d`：

```json
{ "from":"...", "to":"...", "bucket":"1h",
  "totals": {"requests":127,"ok":113,"fail":14,"retries":23,"unmapped":4,
             "p50_ms":10300,"p95_ms":69800,"max_ms":2832000},
  "buckets": [ {"ts":"2026-10-20T12:00:00+08:00","requests":9,"ok":8,"fail":1,"retries":2,"unmapped":0} ] }
```

- 为什么必须有：首屏状态带与直方图**不能靠前端拉 2,000 条现算**（2,000 条只覆盖 9.66h，且 844 KB/次）。
- 代价：一次倒读扫描（1 小时 = 几十 KiB；7 天 ≈ 全文件的 12%）；建议服务端 5 秒结果缓存（key = `from|to|bucket`）。

### 8.4 实时增量（低成本版，建议一期就做）

`GET /api/call-log?after=<ts>&format=2&limit=100` 正序返回 —— 前端 5s 轮询（**替换**现在"整表重拉 500 条 + innerHTML 全重绘"），只 append 新记录并按 `req_id` 去重。SSE（`/api/call-log/stream`）留到二期：改造量更大（要跨进程通知），而 5s 轮询足够。

### 8.5 两个"顺势回答"的问题

#### (a) "23 万行怎么查"的正确解法

**倒序游标（A）先做，按天分文件（B）后做**，对比见 §3.2。要点：
- A 的关键不是"分页参数"，而是**倒读实现**（复用 `tailReadLastLines` 的从尾往前、按块读、命中即停）——实测一页 1 MiB / 1.7 ms，最坏 118 MiB / 14 ms（页缓存热）。
- A 的唯一缺陷是"不能跳天、不能跨页随机访问"，但日志页的交互就是"往前翻"，不需要。
- B 的收益是"跳天/归档/单日并行聚合"，代价是**动写入与统计读取两条路**，风险高 ⇒ 建议做成独立任务，验收门禁 = "同一份数据，`/api/stats` 每个数字逐字节一致"。
- **不需要**内存索引/数据库：一个 118 MiB 的顺序文件 + 倒读 + 每页 500 条，在这台机器上完全够（B 的索引也只是"每天一条元数据"，几十 KB）。

#### (b) 未来的路由决策怎么落日志：一条请求一行，还是每次尝试一行？

**建议：一条请求一行（主记录不变）+ `events[]` 里新增 `route` 事件 + record 级三个字段。**

| 方案 | 形态 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **① 一条请求一行（推荐）** | `CallRecord` 加 `routed_from` / `route_pick_reason` / `route_candidates`；`events[]` 加 `{type:"route_pick", detail:"逻辑名→选中模型", at}` | 列表/聚合天然按请求聚合；**不破坏现有 `status`/成功率口径**（请求级，见 spec D3）；重试信息本来就在 events 里 | 一次路由多个候选时 detail 较长（用 `route_candidates` 数组字段解决） |
| ② 每次尝试一行 | 每次上游尝试一条记录 | 尝试级统计最细 | **破坏**"请求级成功率"口径（分母变尝试数）；`unmapped`/`models` 聚合会漂移；历史 23 万行是请求级的，混两种粒度 = 灾难 |
| ③ 独立 `routing.jsonl` | 路由决策单独一条流 | 主文件零改动 | 列表页要 join 两个文件（后端要么全读一遍，要么前端两次请求），且"一次请求的路由决策"会与主记录时序错开 |

⇒ 选 ①。对列表/聚合的影响：
- 列表：卡头可多一个「路由」徽章（`routed_from` 存在时显示 `逻辑名 → 实际模型`）；老行无该字段 → 不显示（不是显示"未路由"）。
- 聚合：可以按 `routed_from` 分组算"每个逻辑名被换了几次/成功率"，但**必须显式加参数**（`group_by=routed_from`），且**不改变现有 `models` 聚合**。
- 日志量：一条请求 +1 个事件（约 120 B），按 7,636 条/日 ⇒ +0.9 MB/日，可忽略。

### 8.6 落地顺序建议（给 Lead 排任务）

2. **字段 P2**：`model_in` / `attempt_count` / `outcome` / `gen_ms` / `retry_wait_ms` / `events[].attempt,dur_ms`（只加键 + 只在新行写；`model_in` 单独先做，因为未映射排查最痛）。

### 9.2 为什么是"一页两个子视图"而不是两个页面

三条理由（与 Lead 判断一致，这里补上可验证的支撑）：

1. **同一份数据两种视角**：分析是 `GROUP BY`，明细是 `ORDER BY ts DESC`；数据源都是 `/api/call-log`，拆页面会变成两份加载逻辑、两套筛选状态。
2. **联动是核心用法**：「分析里看到某个模型的 p95 高 → 立刻看这个模型的逐条请求」。拆两个页面这一步要靠"复制筛选条件再跳转"，等于让用户手工搬运状态。
3. **顶部导航已有 6 项**，第 7 项会让"日志"这个词指向不明。

实现上子视图是**同页面内的两个 pane**，切换只改 `body[data-sub]` + `hidden`，不重新加载、不丢筛选状态。

### 9.9 verify.py 门禁（本轮新增，全绿）

```
cd docs/mockups/u3 && python3 verify.py logs-v2.html
→ ALL_PASS: True   PASSED_STATES: 63 / 63
python3 verify.py          # 全量套件（7 个文件）
→ ALL_PASS: True   PASSED_STATES: 161 / 161
```

断言要点（每条都在 `logsProbe()` 里，能在 63 个状态上重复执行）：

1. **方向唯一**：`#dirs` 3 个按钮、任何时刻**只有 1 个方向**可见（分析/明细面板任一可见即算该方向可见）；
2. **子视图唯一**：`#subsw` 2 个按钮、只有 1 个子视图可见、`body[data-sub]` 与实际可见面板一致；
3. **分析侧内容**：KPI **6** 张、小时柱 **24** 根、分布行 **≥12** 行、路由预留 **3** 个字段（`route_candidates` / `route_pick_reason` / `routed_from`）；
4. **明细侧编码**：状态徽章 `≥3` 个且**每个都"符号 + 中文"**（`✓✕⏱↻?⊘→` + 文字），不全靠颜色；页面文本里 `未映射` / `闸门拒绝` / `超时` 各自 **≥1** 次；统计条 `data-will-hold` = 4 个（`clTotal/clFail/clRealRate/clIssue`）；
5. **只读预留**：带 `data-future-field` 的容器内 **0 个 input/select/textarea**（是只读展示，不是假只读）；
6. **联动**：`jump*` 三态必须"切到明细 + 显示筛选来源 + 可见条数严格小于全量"；
7. **抽屉**：`drawer` 态必须真的 `.on`，其余态不许在打开状态；
8. **筛选真的生效**：`unmapped` 2/24、`slow` 4/24、`today` 22/24、`incoming` 24→25 条；
9. **不溢出**：1440/390/320 三档 `scrollWidth === clientWidth` 且**未用** `overflow-x:hidden` 掩盖（320 下修掉三处真溢出：方向切换条换行、分布列 `min-width:0`、页脚长文本断行）；
10. **零外部请求 + 双主题**：`requests_non_file_count === 0`，主题切换后 `css_live === true`。

> 过程里踩到的两个"假通过"陷阱，已写进断言防回归：① 设置页和日志页都有 `#dirs`，探针靠 `body[data-page]` 区分，否则设置页探针会在日志页误判；② 抽屉关闭时是 `translateX(101%)` 移出画布，若不设 `visibility:hidden`，探针会把画布外元素算成溢出。

### 9.11 待你/用户拍板

1. **选哪个方向**：我推荐 **③ 聚合故事线**（卡头一句结论 + 尝试阶梯 + 耗时分解，最贴"排障"）；但 ② 的明细表格对"扫一遍找异常"最快，若用户更常"翻明细"就选 ②。① 在手机上读白描成本最高，不建议。
