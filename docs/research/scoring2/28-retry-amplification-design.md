# 重试放大防护（N4 候选）

> 起因：用户指出「客户端看到 429 第一反应是重试，自动化会无条件重试」。
> 结论：防线不能只靠「快速返回 429」，必须**吸收 + 去重**，否则压力从上游转移到网关自身。

## 1. 单飞合并（最高优先级）

- 键：`model + sha256(canonical(body))`（去掉无关键，如 `metadata`）。
- 同一键的并发请求只发一次上游；后到者等待同一个结果（成功结果可在短窗口内复用，
  失败按原状态返回）。
- 效果：自动化重试风暴不会产生任何新上游 attempt，也不会消耗新出口。
- 约束：仅对非流式与「尚未开始输出」的流式请求合并；已开始输出的流式不能合并。
- 窗口：键在最后一次 attempt 结束后保留 2s（只共享同一批并发，不做缓存）。

## 2. 配额冬天用「短等待」代替立即 429

- 触发（池级）：滑窗最近 50 次中 429 占比 >70% 且涉及 ≥5 个不同出口。
- 行为：请求进有界队列（32），最多等 8–15s 抢 1 个哨兵探测名额；
  抢到则正常执行，超时才返回 429，带 `Retry-After: 30`。
- 哨兵：3 个固定出口，单在途，失败即换下一个；全部失败则翻倍 TTL（15→30→60min）。
- 任何情况下全池上游 attempt 速率 ≤1/s。

## 3. 客户端侧配额

- 按 API key / 来源 IP 令牌桶（默认 10 rpm，可配）。
- 超限立即 429 + `Retry-After`，不消耗上游、不进队列；把队列留给正常用户。

## 4. 与 v5 的接口

- `poolGate`（新）：`v5AdmitContext` 在 `AdmitPreferred` 之前问一次
  `gate.Allow(now)`；返回 false 时不取租约，main 进入队列等待而不是直连兜底。
- 计数来源：`v5AppendOutcome` 已有的 outcome 事件，滑窗在内存里维护，
  不引入新的落盘格式。
- 单飞表与 `Admission` 同生命周期（内存），重启即清空。

## 5. 验收

- 回放：用 10-27 11:00–12:22 的日志构造并发重试，证明单飞后上游 attempt 数不随
  客户端重试次数增长。
- 变异：去掉单飞键的 body hash、把队列上限改成 0、把 `Retry-After` 去掉，
  对应测试必须红。
