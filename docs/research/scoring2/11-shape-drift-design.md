## 0. TL;DR（结论先行）

1. **初判方向对，但不是根因的全部；「这是 shape 级拒绝」这个前提本身是错的。** 18:03–23:07 的 11,408 条 429 失败，证据指向 **(a) 单节点/单模型免费配额耗尽 100%**，**(b) 全池同模型耗尽 0%**，**(c) 上游 shape 级拒绝 0%**。闩死是「配额耗尽的正常 429」被守卫**误判**成 shape 风暴后形成的吸收态；不是上游真的在按形态拒绝。
2. **旧闩的三处机械缺陷都成立**（同出口重复刷新、窗口空才解除、全局不分模型，`shape_drift.go:33,63,68`），但只修这三处不够。更靠前的两个缺陷是：
   - **触发判据本身是伪信号**：10 分钟内 3 个不同出口 429 在高流量 + 212 节点池里是**常态**。10-22 在 14:01 拉起闩并保持 **9h20m**，期间 1,893 条成功、40 个不同出口成功；10-23 拉起后保持 **11h52m**，831 条成功。旧闩 5 天里 4 天被拉起，只有 10-26 造成灾难 —— 因为只有 10-26 的「当前 sticky 出口」恰好长期配额耗尽。
   - **命中闩后仍会持续打当前出口**：`haltDrift` 只禁止**切换**，不禁止**继续请求当前出口**（`main.go:3208-3215`）。真 shape 风暴下，当前 IP 会在很短时间内吃满 ~16 次坏形态（事故峰值 181 请求/分钟 ⇒ 约 5 秒），半开试探只能减慢「换下一个 IP 烧」的速度，不能保护当前 IP。
3. **量化答案**：
   - 闩死期间 **11,408/11,408（100%）** 的 429 失败都至少存在一个「同模型、不同节点」在 19:20–19:59 成功过的证据（61 个 `(node, model)` 对、768 条成功）；用唯一一段「未闩死且高流量」的 19:20–20:00 做行为对照，**61 次 429→切换里 57 次成功（93.4%）**，据此估计约 **10,650 条**本可恢复。
   - 半开试探（T6 现规格：每 model 每 60→300s 一次）在真 shape 风暴下的新 IP 烧毁速率上界是 **R_new = M/B ≈ 2/300s ≈ 24 IP/小时**（M=2 个 model），**212 个 IP 约 8.8 小时烧完**；若 M=85 个免费 model、B=300s，则 5,100 次探测 / 212 ≈ **24 次/IP/5h，已超过实测 ~16 次的封禁阈值**。且当前实现下**当前出口仍被全量请求打**，封禁时间 ≈ 16/λ，λ=3 req/s 时约 5 秒。结论：**按 T6 现规格，「不会把 212 个 IP 逐个烧掉」不成立**；必须加「命中后全局 fail-fast + 全局单飞探测 + 每 IP 探测冷却」。
4. **推荐方案**：把「全局 shape 闩」降级为「**按 (model, egress) 的配额排除 + 连续切换失败后的全局单飞试探**」：
   - 正常态：429 → 只排除 `(model, egress)`（TTL 递增，5m→30m→2h→5h），换下一个未排除出口；成功即清除并重置。
   - 疑形态态：连续 K 次「换了新出口仍 429 且期间零 2xx」才进入；进入后**全局每 model 同时只允许 1 个上游探测**（60/120/300s + 抖动），其余请求直接 503/429 fail-fast，**不再打任何出口**；10min 硬 TTL、任一 2xx 立即退出。
   - 与 T2 池级 403 halt、quota_halt、NodeExhausted 的优先级与矩阵见 §8.2；核心原则：**429 不直接 mark NodeExhausted**，改由「切换后成功」确认再 mark（T1 confirm-then-mark 同构），否则就是本次事故里「halt 跳过 mark，真正的坏节点永远不被隔离」的反面。
5. **对当前工作区 T6 实现的结论**：方向（首次时间、TTL、按 model、半开）正确，但**触发条件仍用「3 出口/10min」伪信号、命中后仍全量打当前出口、按 model 放大会放大探测速率**。建议按 §8 改后再上；否则下一次高流量配额耗尽仍可能复发（只是从「永久闩死」变成「每 10min 抖一次 + 慢速烧 IP」）。
6. **闩死还会污染打分数据（Lead 追加，已量化）**：塌陷期 18:12:56–23:07:25 共 11,453 条请求只落在 **11 个 `(model,node)` 对 / 7 个节点**上，其中 3 个节点占 **99.84%**；S19 的 67 个「已知可用」对里有 **64 个（95.5%）在 4h23m 内零尝试**；按 2 model × 139 available 估算，最多 **267/278（96.0%）** 对没有任何新观测。旧闩对这些被抑制的尝试 **0 条结构化记录**（只有 `shape_drift` 聚合事件），离线回放无法区分「没试过」和「试了失败」，是典型 MNAR。**因此新设计把「逐次记录被抑制的 attempt」列为硬门槛**：字段 `model`、`node_fp`、`suppressed_by`（shape_drift/pool_halt/quota_halt/node_cooldown）、`would_be_egress`；不记录的方案判不合格（详见 §5.5、§6.2、§8.3）。

### 1.2 口径

- **429 识别**：`err_msg` 含 `429`，或任一 event 的 `detail` 含 `quota_signal` / `FreeUsageLimitError`。`call_log` 的 `nodes` 数组按 attempt 追加（一次尝试一个 fp；重试成功会有 2 个），因此 `len(nodes)` 可近似 attempt 数；本报告另用 events 交叉核对。
- **闩死失败**：`status=fail` 且 `err_msg=upstream http 429`，落在闩的**生效窗口**内；成功但先吃 429 的记录（`status=ok` 且 events 有 429）不算失败，单独用于「切换后成功」。
- **闩窗口**：按旧实现的精确状态机重放（`/tmp/t6a/sim_guard.py`：10min 窗口、同 fp 刷新、3 个不同 fp 拉起、窗口空才解除）。重放结果与 `shape_drift` 事件、`nodes` 长度、`until` 时间三方交叉一致。
- **有额度证据集** `S19`：`19:20:00–20:00:00` 内 `status=ok` 的 `(node fp, model)` 对。选这段的原因：它是本次事故中唯一「闩未生效 + 切换正常工作」的 40 分钟窗口（768 条成功、**67 个 `(node,model)` 对、61 个不同节点**）。这是 Lead 指定的「19:00 前后成功过」证据，本报告**把它当上界**，并额外用行为对照（全切换 93.4%，配额切换 92.7%）给现实估计。
- **塌陷窗（C）**：`18:12:56–19:20:00` ∪ `20:00:00–23:07:50`，即两个闩生效、且真正开始全灭的区间；与「闩 armed 窗口」区分（后者含拉起前的正常期与自然滑空期）。
- **抑制尝试（suppressed attempt）**：本应发生、但因闩/池级 halt/出口熔断/节点冷却而**没有发出的上游 attempt**。旧代码不记录该事件，本报告只能用「每条 429 失败至少少切 1 次」推下界、用 `maxQuotaSwitches=5` 推上界；新设计的硬要求是逐次落日志（§8.3）。
- **根因判据**（详见 §4）：
  - (a) 单节点/单模型配额耗尽：同一 `(node,model)` 返回 FUL，但**同模型的其它 node 在同一时段有 2xx**（或该 node 的另一个 model 仍可 2xx）。
  - (b) 全池同模型耗尽：同 model 在**所有可观测 node**上都无 2xx，且**其它 model 有 2xx**；池中无任何可用 node 能接该 model。
  - (c) 上游 shape 级拒绝：与 node 无关，**换一个全新出口仍 FUL**，且 body/版本/形态在成功与失败请求之间无可观测差异；恢复只能靠改形态/版本，不能靠换 IP。

### 2.4 关键恢复点不是「闩自己好了」

| 时间 | 事件 | 证据 |
|---|---|---|
| 19:18:17 | `51924bd3` 因 `connect_error: ... context deadline exceeded` 被标 **dead**（不是 exhausted） | app log `node state changed state=dead`；60s 超时是闩下持续打同一节点的副作用 |
| 19:20 | 池子 pick 到 `cbaac8eb`，请求恢复 | call_log P2 768 成功 |
| 20:30:13 | `f33f790b` 同样因 60s `connect_error` 被标 dead，池子换 `30a03abd` | app log |
| 23:03:55/58 | `4ad1982e`、`8ffdd871` 的 5h exhausted 到期自动恢复（18:03 被 mark 的两个） | app log `node auto-recovered from exhausted` |
| 23:07:42 | 切到 `27436cb4`（app log 无 manual/restart；容器未重启、无 config 变更） | call_log 首条成功；容器 `StartedAt` 未变 |

**结论：两次「恢复」都不是闩的解除逻辑生效，而是节点被超时打死后池子被动换节点、或外部切换。** 闩本身在这 5 小时里从未主动放行过任何一次配额切换。

### 2.5 「复发」是真的第二次独立拉起

第一次闩在 `19:33:23`（最后一次 429 后 10min）自然滑空；`19:20–19:59` 切换完全正常，61 次 429→切换 57 次成功。`19:51` 与 `19:59` 的正常配额耗尽让窗口里再次出现 ≥3 个出口（`645bc73b`、`826a1223`、`f33f790b`、`30a03abd` 等），`20:00:08` 闩再次拉起；这一次当前节点连续 429 不断刷新同一条记录，直到 `23:07` 再也没能自己解除。**同一份日志里两次拉起、两次都靠外部/超时脱困，排除了「一次性上游抖动」的解释。**

## 3. 旧闩实现机制解剖

### 3.1 代码事实（HEAD `3ab39e9`）

```go
// shape_drift.go:31-37（HEAD）
shapeDriftSeen    = map[string]time.Time{} // egressKey -> 最近一次 FreeUsageLimitError
shapeDriftWindow  = 10 * time.Minute
shapeDriftMinimum = 3
shapeDriftArmed   = false

// shape_drift.go:57-76（HEAD）
for k, ts := range shapeDriftSeen {
    if now.Sub(ts) > shapeDriftWindow { delete(shapeDriftSeen, k) }
}
if shapeDriftArmed && len(shapeDriftSeen) == 0 { shapeDriftArmed = false }
shapeDriftSeen[egressKey] = now          // ★ 每次 429 都刷新
if !shapeDriftArmed && len(shapeDriftSeen) >= 3 {
    shapeDriftArmed = true
    return true, true                    // halt
}
if shapeDriftArmed { return true, false } // halt
```

调用点（HEAD `main.go`）：

```go
// main.go:3193-3215
if quota, quotaReason := classifyQuota(resp.StatusCode, errBody); quota {
    callLogEvent(... "http %d quota_signal")
    haltDrift, driftConfirmed := shapeDriftShouldHalt(egResult.EgressKey(), quotaReason, time.Now())
    ...
    if haltDrift {
        // 不切节点、不 mark：漂移期 mark 会把健康出口误标 exhausted。
        lastBody, lastStatus, lastHeader = errBody, resp.StatusCode, resp.Header
        lastErr = fmt.Errorf("upstream error")
        break                    // ★ 只结束本请求；下一个请求还会再来一次
    }
    if nodeFp != "" && quotaSwitches < maxQuotaSwitches {
        proxyPool.mark(nodeFp, NodeExhausted, "quota:"+quotaReason) // 只有未 halt 才 mark
        ...
    }
}
```

三个直接缺陷（与初判一致）：

1. **同出口刷新**：`shape_drift.go:68` 每次 429 覆盖时间戳，不是「首次」。
2. **无 TTL、解除条件只有窗口空**：`shape_drift.go:63`；而第 1 条保证只要当前出口持续被请求并 429，窗口就永不空。
3. **全局单桶、不分 model**：`shape_drift.go:33` 的 key 只有 egress，没有 model；mimo 的配额耗尽会把 deepseek 的切换一起闩死。

### 3.2 吸收态证明（为什么 5 小时出不来）

设当前 sticky 出口为 `E`，请求到达率为 λ > 0，且每次到 `E` 都返回 FUL。每次请求执行：

```
seen[E] = now          // 刷新
armed == true          // 已拉起
return halt            // break
```

于是 `age(seen[E]) ≈ 1/λ`（事故峰值 λ≈3/s，谷值 λ≈0.05/s），永远 ≪ 10min；`len(seen) ≥ 1` 恒成立，`len == 0` 永不满足 ⇒ **armed 状态是吸收态**。能离开的路径只有三条，全部是外部事件：

1. 当前出口在 >10min 内**完全不再收到请求**（λ→0，例如夜间无流量）；
2. 当前出口被**传输错误**标 dead、池子换到健康节点（本次 19:18、20:30 就是这样，代价是 60s 超时）；
3. 人工切节点/重启进程（本次 23:07）。

### 3.3 触发判据是伪信号：3 个出口/10min 在高流量下是常态

| 日期 | 429 事件 | 任意 10min 窗口内 ≥3 个不同出口的窗口数 | 单窗口最大不同出口 | 旧闩拉起次数 | 拉起后窗口内成功/出口数 |
|---|---:|---:|---:|---:|---|
| 10-21 | 0 | 0 | 0 | 0 | — |
| 10-22 | 50 | 42 | **23**（14:03） | 2 | **1,893 成功 / 40 个出口**（最长 9h20m） |
| 10-23 | 46 | 22 | **13**（11:58） | 3 | **831 成功 / 45 个出口**（最长 11h52m） |
| 10-24 | 548 | 490 | 77 | 13 | 0（但主错误是 403，属 T1 事件，不作 429 证据） |
| 10-26 | 11,475 | 736 | 5 | 2 | 第一次拉起窗口内 **377 成功 / 31 个出口** |

- 10-22 的 14:03 窗口里 **23 个不同节点**都在 10 分钟内报过 FUL，但当天 14:00 之后仍有 1,893 条成功、40 个不同出口成功；这只能是「多节点配额先后耗尽、其余节点仍可用」，不可能是「全池 shape 被拒」。
- 10-23 最长一次闩持续 **11h52m**（00:02–11:54），期间 831 条成功；如果这 11 小时真的是 shape 级拒绝，不可能有成功。
- 10-26 第一次闩的窗口内也有 377 条成功（18:04–18:12 的 217 条 + 19:20–19:33 的 160 条），**闩拉起 ≠ 全网被拒**。
- 反过来说：5 天日志里**没有任何一次**「切换仍可用、但所有出口对同一形态都 429、且 0 成功」的时段。也就是说，旧闩要防的「真 shape 风暴」在可观测数据里**一次都没出现过**，它却因正常配额churn 拉起了 20 次。

### 3.4 命中闩后仍然打当前出口：烧 IP 保护是假的

`haltDrift` 分支只 `break` 本请求，**不做以下任何一件事**：

- 不把当前出口从 `pick` 候选里排除（`ExcludeEgress` 只在 T6 工作区版本里有，HEAD 没有）；
- 不 mark、不冷却当前出口；
- 不拒绝后续请求的上游调用；
- 不限制并发。

所以真 shape 风暴下，当前 IP 仍按 λ 收到坏形态请求：事故峰值 λ≈3/s，**约 5 秒就达到实测 ~16 次的封禁阈值**；5 小时累计 11,408 次 429（本次因为是真配额，所以只 429 不封）。旧闩唯一做到的是「不把坏请求扩散到更多 IP」，代价是牺牲全部可用性。

### 3.5 与 `NodeExhausted` 的冲突：该隔离的节点反而不被隔离

`main.go:3208-3215` 的 halt 在 `proxyPool.mark(...NodeExhausted...)`（`:3218`）之前 `break`。后果：

- `18:12:56` 起真正配额耗尽的 `51924bd3` **从未被标 exhausted**，于是一直是 sticky 当前节点，持续吃 5,114 次 429；
- 只有 `18:03:55/58` 闩拉起**之前**的两次切换才 mark 了 `4ad1982e`/`8ffdd871`（`until=23:03:55/58`，5h，`config.node_cooldown_exhausted_hours=5`）；
- 池子真正换节点靠的是 60s 连接超时触发的 dead（`effectiveDeadCooldown` 配置 5min），不是配额状态。

这条冲突是「闩死 5 小时」的直接放大器：**闩既不让换，又不让标，当前节点只能靠超时或人工才能离开。**

### 3.6 Sticky 单出口放大：212 个节点在事故里只出现 11 个

`egress.go:239,314-327`（HEAD）：

```go
stickyPublic = "cli://public-shared" // 无会话标识的 public 请求共用同一出口
func stickyKeyForRequest(...) string {
    if auth.Token != "" { return "tok:" + auth.Token }
    ...
    return stickyPublic
}
```

事故日志里 10 分钟桶的失败节点数**几乎恒为 1**（§2.3），5 小时共只触及 11 个 fp。这不是池子只有 11 个节点（`proxy_state.json` 明确 **212** 个），而是所有 public 流量共用同一个 sticky 出口。因此：

- 「(b) 全池同模型耗尽」在观测上**根本无法用请求日志证明**（我们只在看一个出口）；
- 但反过来，19:20–19:59 的 30+ 个成功出口、23:07 的新出口成功，足以**否定**「全池都不可用」；
- 事故的真实形态是「**单出口配额耗尽 + 闩禁止换出口**」，而不是「池子整体没额度」。

## 4. 三种根因假设的判定

### 4.1 判据表（先定义怎么区分，再看数字）

| 判据 | (a) 单节点/单模型配额耗尽 | (b) 全池同模型耗尽 | (c) 上游 shape 级拒绝 |
|---|---|---|---|
| 同模型换 node 是否 2xx | **是**（关键判据） | 否（所有 node 都 429） | **否**（换新 IP 仍 429） |
| 同 node 换 model 是否 2xx | 可能（不同 model 配额独立） | 可能（别的 model 还有额度） | 否（形态与 model 无关） |
| 429 body 是否与配额耗尽一致 | 是（FUL） | 是（FUL） | 是（FUL，伪装） |
| 是否依赖版本/形态变更才恢复 | 否（换 IP 即可） | 否（等配额重置即可） | **是**（换 IP 无效，必须改形态/版本） |
| 恢复后的首个请求是否无需改版本就 2xx | 是 | 是（配额重置后） | 否 |
| 直连出口是否同时 429 | 不要求 | 可能 | 通常也 429（同形态） |
| 失败是否从某节点/某模型开始逐步扩散 | **是**（per-node/per-model 边界） | 是（全 model 同时） | 是（全 model 同时） |

### 4.2 结论数字

| 根因 | 归因的 429 失败 | 占 11,408 | 证据强度 |
|---|---:|---:|---|
| (a) 单节点/单模型配额耗尽 | **11,408** | **100%** | 强：per-(node,model) 边界 + 池内 61 个 `(node,model)` 有额度 + 两次换节点即恢复 |
| (b) 全池同模型耗尽 | **0** | 0% | 反证：P2 61 个 `(node,model)`、30+ 节点、768 条成功；P3 的 `20:00:03–05` 还有 6 条成功在 `0fa97a5a` |
| (c) 上游 shape 级拒绝 | **0** | 0% | 反证：同一进程/版本/形态在一小时前和 `23:07` 后都能 2xx；恢复靠换 IP，不靠改形态/版本 |

**为什么不是 (c)（最重要）**：

1. 10-25 对照实验的结论是「形态三层（TLS/头/body）任一不符 ⇒ 429，且反复触发封 IP」（`oc_shape_v2.go:1-26`、`bun_transport.go:1-23`）。形态校验是**按请求形态**的：同一个网关、同一版本、同一 body 构造，换一个出口 IP 不会改变形态，若真是形态被拒，`27436cb4` 在 `23:07:42` 的**首个**请求就该 429；它却直接 200（`ttft=8.1s`），随后 545 条全成功。
2. 两次恢复（19:18 dead→`cbaac8eb`；23:07→`27436cb4`）都**没有**重启、没有 `config hot-reloaded`、没有版本变更：容器 `StartedAt=15:16:56+08`、`RestartCount=0`；应用日志 10-26 只有 15:16 一条 `server starting`；`ocClientVer=1.19.4` 未变。形态没变，能恢复 ⇒ 不是形态。
3. 429 body 完全相同（`FreeUsageLimitError` / `Free usage limit reached`），单凭 body 确实无法区分 (a)/(c) —— 这正是 10-25 的结论；但**换 IP 可恢复**这一行为判据足以把 (c) 排除。

**为什么不是 (b)**：

- P2 的 19:20–19:59 有 **768 条成功、61 个 `(node,model)` 对、30+ 个不同节点**；如果是全池同 model 耗尽，这些成功不可能发生。
- P3 的 `20:00:03–05` 还有 6 条成功的 mimo 请求在 `0fa97a5a`（`duration 23–45s`，`ttft 4–8s`），说明闩 2 拉起时池里仍有可用额度；它们只是**已经在该节点上**的 in-flight 请求，后续请求全部被闩按死在 `f33f790b`/`30a03abd`。
- `proxy_state.json` 有 212 个节点、`available=139`（23:58），不是「池空」。
- 唯一无法直接观测的是「P3 期间其它 211 个节点是否也都配额耗尽」；但 sticky 让请求只落在 1 个节点上，**没有证据**支持全池耗尽，而且 23:07 的新节点立刻可用，已足够否定。

**为什么 (a) 是 100% 而不是「大部分」**：

- 每条 429 失败都发生在**具体节点 + 具体模型**上；同一 `(node, model)` 在 19:20–19:59 有成功记录（§5 的 100% headroom），且失败节点的模型切换边界可观测：`51924bd3` 的 mimo 首个 429 是 `18:12:56`，deepseek 首个 429 是 `18:15:02`（相差 2m06s）——两个模型的配额计数是**分开**的；`30a03abd` 的 mimo 首个 429 是 `19:59:59`、deepseek 是 `20:29:13`（相差 29m14s）。这正是 (a) 的 per-(node,model) 特征，而不是 (c) 的「形态一坏全坏」。
- 唯一可归因给「非配额」的是 P1 的 2 条 502 和若干 connect_error；它们不在 11,408 里，单独列出。
- 需要诚实标注：这是**行为归因**，不是上游配额 API 的直接读数；没有 `dial_ms`、没有配额余量字段，无法给每条请求盖 100% 的章。但「(c) 需要换 IP 也失败」这个必要条件被两次换 IP 成功直接推翻，因此 (c) 的上界是 0。

### 4.3 分阶段/分模型

| 阶段 | 429 失败 | mimo | deepseek | 说明 |
|---|---:|---:|---:|---|
| P1（18:03:51–19:20） | 5,113 | 4,711 | 402 | `51924bd3` 单节点；mimo 先耗尽（18:12:56），deepseek 后耗尽（18:15:02） |
| P3（20:00–23:07:50） | 6,295 | 3,890 | 2,405 | `f33f790b`（20:00–20:30）+ `30a03abd`（20:30–23:07）；两个 model 都打在同一节点 |
| **合计** | **11,408** | **8,601 (75.4%)** | **2,807 (24.6%)** | — |

### 4.4 触发因 ≠ 伤害因

必须把两件事分开：

- **触发因**：`18:03:51–18:03:58` 的 3 个不同出口 429（`4ad1982e`、`8a3acdda`、`8ffdd871`）。这三条是**真配额**：前两个在 `18:03:55/58` 被标 `NodeExhausted`，`until=23:03:55/58`，5 小时后自动恢复。它们本身完全正常。
- **伤害因**：旧闩把「3 个出口在 10min 内 429」解释成形态风暴后，**禁止了后续所有配额切换**；而它又跳过 mark，导致真正耗尽的 `51924bd3`/`f33f790b`/`30a03abd` 永远不被隔离。**没有闩，这只会是 3 次正常的节点切换；有了闩，才是 11,408 次失败。**

### 4.5 反例检查：有没有可能是「高流量把池子打空」

- 事故峰值 181 请求/分钟，但 212 个节点、每节点每日免费额度未知；P2 的 19:20–19:59 在 768 条成功之后仍有 30+ 节点可用，说明池子并未在 19:59 前耗尽。
- 20:00–23:07 的 6,295 条请求全部落在 2 个节点上（sticky + 无切换），**没有向其它节点分摊**；因此「打空全池」在机制上不成立——流量根本没到其它节点。
- 23:07 切到 `27436cb4` 后 545 条全成功，若池子真被 20:00–23:07 的流量打空，新节点不可能有额度。
- 结论：(b) 不是本次主因；即使局部存在「多节点配额也耗尽」，也不是造成 11,408 条失败的必要条件，闩才是。

## 5. 「本可切到有额度节点」量化

### 5.1 证据集与定义

- `S19`：`19:20:00–20:00:00` 内所有 `status=ok` 的 `(node, model)` 对 = **67 个记录、61 个不同节点**（30+ 个不同 fp；67 条成功请求使同一 `(node,model)` 重复）。
- 对每条闩死期 429 失败 `r`：`alt(r) = ∃(node≠r.node, model=r.model) ∈ S19`。即「同模型、换个节点就有额度」。
- 为了避免把「几小时前的证据」当永恒事实，另给两种更严格的变体：
  - `prev60m` / `prev15m`：在失败前 60/15 分钟内，**同模型、不同节点**有真实 2xx；
  - `next60m`：失败后 60 分钟内，**同模型、不同节点**有真实 2xx（事后证据，用于看「如果当时切过去」）。
- 行为对照：P2 里真实发生「429 → 换节点」的请求，最终 2xx 的比例；这是**同一份 workload、同一批节点、只差闩是否放行**的自然实验。

### 5.3 为什么 92.7% 是比 100% 更可信的中心估计

- S19 的 100% 是**上界**：它证明「这些 `(node,model)` 在 19:20–19:59 有额度」，但不能证明 22:00 时它们还有额度。
- `prev15m` 的 20.6% 是**下界**：闩生效时所有请求都卡在 1 个节点，**其它节点不会产生成功样本**，所以「没有近期成功」是观测缺失，不是「没有额度」。
- P2 的 41 次切换是唯一一段「同一入口、同一模型、同一节点池、只把闩拿掉」的对照：**38/41 = 92.7%**。它同时包含了「切过去也 429」的真实失败（3 条，全部在 19:59:59 第二次闩拉起那一刻），所以不是只挑成功样本。
- 因此：**11,408 条里约 10,600 条本可以在切换后成功**；剩下的约 800 条可能遇到「新节点也刚好配额耗尽 / 连接错误 / 第二次闩拉起」。这个数不是精确值，但数量级和方向足够支持「这不是不可抗力，是闩造成的可用性损失」。

### 5.5 闩死对打分数据的污染（Lead 追加，量化）

#### 5.5.1 为什么这是「数据问题」而不只是「可用性问题」

打分/选点依赖 `(model, node)` 的尝试样本。旧闩在命中后**静默地**阻止了切换（只记一条聚合 `shape_drift`，不记每次被抑制的 attempt），于是：

- 被钉住的节点承担了**全部** 429 样本 → 它的分数被 1 万条失败压到底；
- 其余可用节点在 4h23m 内**零新样本** → 分数停留在事故前（可能是高分），既没有被证伪，也没有被证实；
- 离线回放只看到「11 个被尝试过的对」，看不到「267 个本可尝试但被抑制的对」 → 这是 **MNAR（missing not at random）**：缺失与否恰好取决于「当前节点是否 429」，而缺失的恰恰是最可能成功的替代节点。把它当随机缺失（MAR）会让打分系统性低估替代节点、并把「只在一个节点上失败」误判成「这个模型整体不行」。

| **被抑制的 `(model,node)` 对（上界）** | **267** | 2 model × 139 available − 11 已尝试 = 267（96.0%） |
| 旧代码留下的逐次抑制日志 | **0 条** | 只有 2 条 `shape_drift` 聚合事件；无 `model`/`node_fp`/`would_be_egress` 逐次记录 |
| 旧代码可区分的「没试过 vs 试了失败」 | **不可区分** | 没有 attempt 记录；只能靠 `nodes` 反推实际尝试 |

> 关键对比：**11 个对**有观测 vs **267 个对**没有任何新观测；其中 **64 个**在 1 小时前刚被证明「同模型可 2xx」。如果打分器按「节点成功率」更新，`51924bd3` 的 5,141 次尝试里 5,112 次失败（≈99.4%）会把它的分数打到接近 0；另外 136 个 available 节点在 4h23m 内一次都没被采样，分数保持事故前状态。**「哪个节点该降权」这件事，旧闩只给了 3 个节点的证据，却让 200+ 个节点逃避了检验。**

#### 5.5.3 硬要求：逐次记录被抑制的 attempt

新设计必须满足（不满足即判不合格，见 §6.2 的门槛列）：

1. **每一次**被 `shape_drift` / `pool_halt` / `quota_halt` / `node_cooldown` 抑制的上游尝试，写一条结构化事件，**不做 10s 去重、不聚合、不采样**（事故量级 ~0.6 条/s，完全可承受；若要控量，只能另加每分钟聚合计数器，不能替代逐次记录）。
2. 字段（至少）：
   ```json
   {
     "event": "quota_attempt_suppressed",
     "ts": "2026-10-26T20:10:03.123+08:00",
     "request_id": "...",
     "model": "mimo-v2.6-flash-free",
     "node_fp": "f33f790b0197d98cecda366df0c4fae1",
     "would_be_egress": "30a03abdbf5e3c703c2b442148547078",
     "suppressed_by": "shape_drift",
     "reason": "armed:model=mimo distinct=4 last_success=20:00:05",
     "switches_left": 5,
     "excluded_count": 3,
     "node_state": "available"
   }
   ```
   - `would_be_egress` 必须在抑制时**做一次不消耗预算的候选计算**填入；若所有候选都被排除，填 `null` 并给 `reason=all_excluded`，同时记 `candidate_count=0`。
   - `suppressed_by` 取**实际生效的最高优先级**（`pool_halt` > `quota_halt` > `shape_drift` > `node_cooldown`），一条记录只归因一个原因；若多因叠加，用 `also_blocked_by` 数组补充。
   - `node_cooldown` 需带 `until`；`quota_halt` 需带 `egress_key`；`pool_halt` 需带 `note403`/`until`；`shape_drift` 需带 `armed`/`distinct`/`last_success`。
3. 埋点位置：不是在 `shape_drift.go` 内部「想记的时候记」，而是在**统一的 attempt 门禁**（`egress.Get` 之后、真正发请求之前）记录；保证所有路径（pool、direct、trial、fail-fast）都经过同一处。
4. 可回放性验收：随机抽 100 条 `quota_attempt_suppressed`，必须能用 `model + node_fp + would_be_egress + ts` 在离线日志里重建「当时若放行会尝试哪个出口」；同一 `request_id` 的 attempt 序列必须能还原成「尝试了 A、被抑制 B、最终 C」。
5. 与打分的接口：离线回放把被抑制的 attempt 标为 **censored**（`outcome=suppressed`），而不是 `success/fail`；打分器必须支持 censored 样本（例如只在「实际尝试」上更新似然，或用 IPW/生存模型），不能把 `suppressed` 当失败。旧闩的「0 记录」让这一步根本无法做。

#### 5.5.4 对「录用标准」的影响

- 任何方案如果只在闩内部加 TTL/半开，却仍**静默抑制**，即使可用性修好了，也**无法修复打分污染** → 在 §6.2 判「不合格」。
- 推荐方案 C10 的 `fail-fast` 也必须逐次记录 `suppressed_by=shape_drift_quota`（或 `probe_only`），否则同样不合格；不能因为「fail-fast 很快」就不记。
- 打分修复本身不在 T6a 代码范围（T6a 只出设计），但本设计把「埋点契约」写死，交给 T6 实现与打分侧（T7?）共同验收。



## 6. 候选方案穷举与打分

### 6.1 评分口径

- **正确性/不误杀（权重 30%）**：正常配额 churn 下不制造全局停摆；真风暴下不做无意义重试。
- **真风暴 IP 保护（25%）**：坏形态请求最多打每个 IP 多少次；是否保护「当前出口」。
- **恢复速度（15%）**：配额/形态恢复后多久重新可用；是否依赖外部重启。
- **复杂度/可维护（15%）**：5 = 最简单；1 = 引入新子系统/配置爆炸。
- **可观测/可回滚（15%）**：能否用日志判断状态、能否一键退回。

### 6.3 每个方案的关键评语（为什么不是它）

- **C1/C2/C4**：都在「如何让旧闩更快解除」上做文章，但旧闩的**触发条件**（3 个出口/10min）本身就是正常配额 churn。10-22 的同窗口最大不同出口是 **23**，10-23 是 **13**；把 TTL 调短只会变成「每 10 分钟重拉一次」，并不减少误判，也不保护当前 IP。
- **C3（T6 现规格）**：`首次时间 + TTL + 按 model + 60s 半开` 修掉了「永久」和「跨模型」两个机械问题，但：
  1. 触发仍是 3 出口/10min，10-22/10-23 的误拉会在新代码里重演；
  2. 命中后 `drift.Halt` 只 `break`，**每个非试探请求仍会打一次当前出口**；真风暴下当前 IP 约 `16/λ` 秒被封（λ=3/s ⇒ 5s）；
  3. `trial` 按 model 各算一份，探测速率 × 模型数；85 个免费 model 时可能 5,100 次/5h，约 24 次/IP，超过 ~16 的封禁阈值；
  4. `trial` 候选只排除「429 集合」，集合 TTL 10min 后会清空，同一 IP 可能被反复试探；
  5. **观测只到聚合层**：`shape_drift` 事件有 `model/armed/distinct/last_trial`，但没有逐次 `node_fp/would_be_egress`，离线仍无法区分「没试过/试了失败」→ §6.2 判 `Partial`，必须补 §5.5.3 的埋点。
- **C5**：把「一个全局闩」换成「按 (model,node) 的软排除」，是本次证据最直接支持的模型（mimo/deepseek 在同节点相差 2m06s / 29m14s 才耗尽）。但**并发风暴**下，多个请求可能在同一 RTT 内同时选中同一个尚未排除的节点，单靠排除不能保证每 IP ≤16 次；需要 C7/C10 的限速与单飞。
- **C6**：抖动只解决「惊群」，不解决「打谁」；在闩死状态下抖动反而让 429 更分散到更多 IP。
- **C7**：通道级限速是必要的安全阀，但它不区分「节点配额」和「形态」；只限速会让恢复变慢（要等 bucket 回填），也不能在节点耗尽时换节点。
- **C8**：删闩是最简单的「不误杀」方案，`maxQuotaSwitches=5` 保证单请求最多 6 个 IP；但在真风暴 + 高并发下，~35 个请求就能把 212 个节点各打 6 次（≈ 每 IP 6 次，且随重试继续上升），**仍会烧池**。它可以作为 C10 的「简化版降级」，不能单独上线。
- **C9**：本次 19:18/23:07 的恢复都发生在**同版本、同形态**下，换 shape/版本不会改变结果；把漂移升级为版本切换会引入版本 churn 和新的 426/区域问题，收益不成立。

### 6.4 推荐：C10 的组成（保留 C5 的模型，借 C7 的限速，用 C6 的抖动，用 C3 的半开但改触发）

1. **per-(model, egress) 排除**（C5）：429 只排除这一对，冷却 `5m→30m→2h→5h` 递增；2xx 清除该对并重置。
2. **per-egress 24h 命中预算**（新增）：同一 egress 在 24h 内累计 FUL 达到 `H_bad`（建议 8）→ 硬排除 24h + 告警；这是「即使状态机出错也不会烧穿」的最后保险。
3. **连续新出口失败检测**（替换 3/10min）：`consecutiveFreshFailures` 只在「尝试了一个**未被排除**的新出口且仍 429」时 +1；任何 2xx 清零。达到 K（建议 5）且期间零 2xx → 进入 `probe_only`。
4. **probe_only 的全局单飞**：每 model 同时最多 1 个上游探测；**全局跨 model 也只允许 1 个**（避免 model 数放大）；间隔 `60→120→300s` 单调递增 + ±20% 抖动；探测候选优先「冷却已到期的已排除节点」，而不是永远挑全新 IP（把「烧新 IP」改成「复测旧 IP」）。
5. **fail-fast**：probe_only 期间，除被选中的探测请求外，其余请求**不调用上游**，直接 503（带 Retry-After）或原 429；**不 fallback 直连**（保护宿主 IP）。
6. **硬 TTL + 成功/TTL 退出**：probe_only 最长 10min；探测 2xx 立即清该 model 状态并退出；TTL 到也退出（但保留排除表与预算，不能靠「TTL 清空」实现恢复）。
7. **禁止 429 直接 mark NodeExhausted**：per-(model,node) 排除已经表达「这个节点这个模型没额度」；全局 NodeExhausted 只留给 403 FreeTier（T1）/探测死亡。若一定要保留面板的「耗尽」语义，只在「切换后另一节点成功」确认该节点配额耗尽时 mark（confirm-then-mark），并限定 5h。

**为什么这比「只加 TTL」或「只删闩」好**：它把「保护 IP」和「保持可用」拆成两个独立机制——**排除表**负责不重复打同一个 IP，**单飞探测 + fail-fast**负责在真风暴下把总请求量压到几十次/5h；而正常配额下切换成功率高（实测 92.7%），几乎不会进入 probe_only。**不需要先判断是 (a) 还是 (c)**，这是它相对旧闩/T6 的最大优势。

## 7. 半开试探的烧 IP 速率上界

> 本节回答两个问题：**(Q1) T6 现规格的半开在真 shape 风暴下会不会把 212 个 IP 逐个烧掉？(Q2) 推荐方案的上界是多少？**
> 「烧掉」定义为：同一 IP 累计收到 ≥H 次坏形态请求，被上游当日封禁。取 **H=16**（`shape_drift.go:26`「实测 ~16 次量级」；`bun_transport.go:17-20` 说「10+ 次后当日封禁」；下面同时给 H=10 的敏感性）。

### 7.1 记号

| 符号 | 含义 | 取值 |
|---|---|---|
| N | 总出口 IP 数 | **212**（`proxy_state.json`） |
| N_eff | 事故期间可用出口 | 120–139（健康探测日志） |
| M | 能独立试探的 model 桶数 | 本次 2（mimo/deepseek）；配置里免费 model 最多 85 |
| B | 单桶两次试探的间隔 | 60→120→300s（上限 B_max=300s） |
| λ | 打到「当前 sticky 出口」的请求速率 | 事故峰值 181/min ≈ **3/s**；谷值 ~3/min ≈ 0.05/s |
| T | 风暴持续时长 | 本次 5h=18,000s |
| Q | T 内总试探次数 | 见下 |
| H | 封禁阈值 | 16（敏感性 10） |
| C | 同一个 IP 两次被试探的最小间隔 | T6 无；推荐 60min |
| H_bad | 每 IP 24h 坏形态预算 | 推荐 8 |

### 7.2 T6 现规格的两个独立问题

**问题 A：当前出口完全没被保护。** `drift.Halt` 只 `break`，每个非试探请求仍会向当前出口发一次上游请求（§3.4）。所以：

```
当前 IP 的坏形态次数 A_active = λ · T
被封时间 t_ban = H / λ
```

| λ | A_active（5h） | t_ban（H=16） |
|---:|---:|---:|
| 0.05/s（3/min） | 900 | 320s ≈ 5.3min |
| 1/s | 18,000 | **16s** |
| 3/s（事故峰值） | 54,000 | **5.3s** |

**结论 A：真风暴下当前 IP 必定在秒级被封；半开试探再慢也救不了它。** 事故里没有封，是因为那些 429 是**真配额**，不触发形态封禁 —— 这恰好说明「用本次日志验证不了烧 IP」，必须靠公式。

**问题 B：新 IP 的试探速率按 model 数放大。** T6 每个 model 独立 `trial`，单桶退避 60→120→300s：

```
Q_T6 ≈ M · (2 + T / B_max)          // 前两次 60s/120s，之后每 300s 一次
R_new = Q_T6 / T = M · (2/T + 1/B_max) ≈ M / B_max
```

| 场景 | Q（5h） | 平均每 IP 次数 Q/N | 是否超过 H=16 |
|---|---:|---:|---|
| M=2（本次） | 2·(2+60) = **124** | 0.58 | 否（但当前 IP 已被 A 烧） |
| M=85（配置上限） | 85·62 = **5,270** | **24.9** | **是** |
| M=2 且 `seen` TTL 10min 允许复用同一 IP | 124，最坏全落 1 个 IP | 124 | 是（若选择器退化） |

**结论 B：**
- 只考虑「新 IP 扩散」，M=2 时 T6 不会把 212 个逐个烧掉（5h 只触及 ~124 次，平均 0.58 次/IP）；**但当前 IP 在 5 秒级被封**。
- **M=85 时会**：5,270 次 / 212 ≈ 24.9 次/IP > 16，等于在 5h 内把池子逐个烧掉。
- 若候选选择退化为「总选同一个 IP」（`seen` 10min 清空、低延迟偏好、picker 粘滞都可能），**M=2 也能烧穿**。
- 所以对 Q1 的准确回答是：**「T6 现规格不会『均匀地』烧掉 212 个，但会先秒烧当前 IP；在 model 数多或选择器退化时，会逐个烧掉」**。不能回答「不会」。

### 7.3 推荐方案（C10）的上界

推荐方案把「正常请求」和「探测」彻底分开：

```
正常请求（probe_only 下）：0 次上游调用（边缘 fail-fast）
探测：全局单飞，Q_C10 = 2 + T / B_max            // 与 M 无关
每 IP 两次探测间隔 ≥ C；每 IP 24h 坏形态 ≤ H_bad
```

代入 T=5h、B_max=300s：

```
Q_C10 = 2 + 18,000/300 = 62 次
触及 IP 数 ≤ min(62, 212) = 62
每 IP 次数 ≤ min(H_bad=8, 1 + T/C) = min(8, 6) = 6   （C=60min）
6 < H=16，余量 10；即使 H=10 也安全
```

| 方案 | 总坏请求 | 触及 IP | 每 IP 最坏 | 被 ban 的 IP | 5h 内会烧掉几个 |
|---|---:|---:|---:|---:|---:|
| T6 M=2 | 124 + λT | 124 | λT（当前）+1 | 当前 IP 1 个 + 可能 0 | **1 个（当前）** |
| T6 M=85 | 5,270 + λT | 212 | ~25 | 当前 + 大量 | **≈212 个** |
| C8 只删闩 | ~6×请求数 | 212 | ~6×RPS/212×t | 视并发 | 数分钟到数十分钟烧完 |
| **C10 推荐** | **62 + 检测前暴露** | **≤62** | **≤6** | **0–1 个** | **0–1 个** |

**检测前暴露**（进入 probe_only 之前）的上界：`E0 = K × C_e`，其中 K=5 次连续新出口失败、`C_e`=单出口并发上限。若把 `C_e` 限制为 4，则 `E0=20` 次，且分布在 5 个不同 IP（每个新出口被排除前最多 4 次），4 < 16；加上探测的 6 次，最坏单 IP 10 次，仍 < 16（H=16）/ ≈ H=10 边缘。**因此建议同时加 `C_e≤4` 与每 IP 24h 预算 8**。

### 7.4 结论（一句话版）

- **是 T6 现规格**：会先秒烧当前 IP；M=2 时新 IP 约 8.8 小时轮完一圈（124 次/5h，平均 0.58 次/IP，单次不封，但选择器退化会集中）；**M=85 时 5h 内每 IP 24.9 次，等于逐个烧掉**。所以「不会烧 IP」是**不成立**的。
- **是推荐方案**：5h 最多 62 次探测、触及 ≤62 个 IP、每 IP ≤6 次，封禁阈值 16（保守 10）以下；**不会逐个烧掉，最坏损失 0–1 个当前 IP**。

## 8. 推荐方案设计

### 8.1 状态机

#### 8.1.1 参数（全部可配置、有默认值）

| 参数 | 默认 | 作用 |
|---|---:|---|
| `K` | 5 | 连续「新出口仍 429」达到 K 次且期间无 2xx → 进入 `probe_only` |
| `last_success_guard` | 60s | 距上次 2xx 不足 60s 时不允许进入 `probe_only`（防抖） |
| `ttl_probe` | 10min | `probe_only` 硬上限 |
| `cooldown_strikes` | 5m / 30m / 2h / 5h | `(model,egress)` 第 1/2/3/4+ 次 429 的排除时长（封顶 5h） |
| `B` | 60s → 120s → 300s | 全局探测退避；乘 1.0–1.2 抖动 |
| `H_bad` | 8 / 24h | 单 egress 24h 内坏形态预算；达到后硬排除 24h |
| `C_e` | 4 | 单 egress 同时在途上游请求上限（含正常与探测） |
| `max_models` | 512 | 模型状态桶上限；LRU 淘汰空闲 >30min 的桶 |
| `max_reentry_per_hour` | 6 | `probe_only` 因 TTL 退出的次数上限，防止「退出→重入」循环烧 IP |
| `allow_direct_in_probe` | false | `probe_only` / 全排除时是否允许回退直连；默认**禁止** |

#### 8.1.2 两层状态

```text
全局（进程内）：
  probeMu, probeInFlight bool          // 跨 model 只允许 1 个探测在途
  nextProbeAt time.Time                // 全局下一次允许探测的时间
  poolHalted bool                      // 来自 T2，优先级最高
  ipBudget[egress] {hits, windowStart} // 24h 滚动

每 model：
  mode: NORMAL | PROBE_ONLY
  exclusions[egress] {until, strikes, lastHit, lastProbeAt}
  freshFailures int                    // 连续「新出口」429 次数
  lastSuccess time.Time
  probeUntil time.Time
  probeBackoff time.Duration
  nextProbeAt time.Time
  reentriesThisHour int
```

> 关键：`probe_only` 是**每 model**的，但**探测令牌是全局单飞**——`M` 个 model 同时进入也只会有 1 个在途探测，避免 §7.2 的 `M` 倍放大。

#### 8.1.3 迁移表

| 当前 | 事件 | 下一状态 | 动作 |
|---|---|---|---|
| NORMAL | 2xx on `(M,E)` | NORMAL | 清除 `(M,E)` 排除；`freshFailures=0`；`lastSuccess=now`；**不清其它 egress 的排除** |
| NORMAL | FUL 429 on `(M,E)`，E 未被排除 | NORMAL 或 PROBE_ONLY | `strikes++`、排除 `(M,E)` 5m/30m/2h/5h；`ipBudget[E]++`；`freshFailures++`；若 `freshFailures≥K` 且 `now-lastSuccess≥60s` → PROBE_ONLY |
| NORMAL | FUL 429 on `(M,E)`，E 已在排除中 | NORMAL | 说明 picker 没排除干净：记 `duplicate_excluded_429`；**不**增加 `freshFailures`；延长 `(M,E)` 排除 |
| NORMAL | 5xx / connect timeout | NORMAL | 走 T3/T2：dead 5m；**不**计 `freshFailures`、不写配额排除 |
| NORMAL | 无候选（全被排除） | NORMAL | fail-fast 503 + `quota_attempt_suppressed{reason=all_excluded}`；不直连 |
| PROBE_ONLY | 非当选请求到达 | PROBE_ONLY | fail-fast 503 + 逐次抑制日志；**0 上游调用** |
| PROBE_ONLY | 当选探测 2xx | NORMAL | 清 `(M,E_probe)`；`freshFailures=0`；退避重置；记 `probe_result=ok` |
| PROBE_ONLY | 当选探测 FUL 429 | PROBE_ONLY | 延长 `(M,E_probe)`、`budget++`、退避升级（上限 300s）、`nextProbeAt=now+B*jitter` |
| PROBE_ONLY | 当选探测超时/5xx | PROBE_ONLY | 清 `probeInFlight`；退避升级；**不**把该 E 标成配额耗尽（除非同时收到 FUL） |
| PROBE_ONLY | 10min TTL 到 | NORMAL | 保留排除表与预算；`reentriesThisHour++`；若 >6 → 继续 PROBE_ONLY（等成功/人工），不再 TTL 退出 |
| 任意 | `poolHalted=true` | 不变（挂起） | 所有请求 503；探测暂停；`nextProbeAt` 顺延到 halt 结束后 ≥5s；不清状态 |
| 任意 | `poolHalted=false` | 恢复 | 探测恢复；`nextProbeAt=max(now+5s, nextProbeAt)`，避免积压惊群 |

#### 8.1.4 探测候选选择（决定 `would_be_egress`）

```text
候选 = 所有 egress
       - dead/exhausted(全局 NodeExhausted)
       - 本 model 的排除未到期者
       - ipBudget 已耗尽的 egress
       - direct（probe 阶段默认禁）
若候选非空：按 (lastProbeAt, lastHit) 最旧优先 → 选 1 个
若候选为空：允许「冷却已到期/最接近到期」的排除项中选 1 个（复测旧 IP，不烧新 IP）
仍为空：fail-fast，不探测
```

- **优先复测旧 IP**：真风暴下所有 IP 都坏，复测旧 IP 不会扩大烧毁面；只有旧 IP 被证明恢复后才逐步回到新 IP。
- `would_be_egress` 必须在**抑制发生时**用同一选择器算一次（不消耗预算、不改 sticky/current），填进日志；不能用「事后猜」。
- 建议给 `egress.Get` 增加 `PreviewOnly bool` 或 `PickPreview(model)`，返回候选但不落 sticky；这是 §5.5.3 观测契约的实现前提。

#### 8.1.5 伪代码（与现有 `main.go` 接口对齐）

```go
// main.go:2957 / 3454 附近，替换 shapeDriftBlockedEgress
```

### 8.2 与 T2 pool403 halt / quota_halt / NodeExhausted mark 的交互矩阵

#### 8.2.1 单一裁决顺序（避免「一个路径放行、另一个还闩着」）

```text
1. auth / model 白名单 / 请求体校验
2. T2 poolHalted?            → 503，禁止一切上游（含探测）
3. quotaRouter.Admit(model)  → PROBE_ONLY 非当选 / all_excluded → 503 + 抑制日志
4. egress.Get(...)           → 选路（排除 dead / NodeExhausted / 本 model 排除 / 预算耗尽）
5. 直连且 quota_halt 已熔断   → 503；probe 阶段默认禁止直连
6. 发上游
7. 响应分类：2xx / 403 FreeTier / FUL 429 / 5xx / timeout
```

**原则**：只有 **2xx 与 TTL/人工** 能解除 `probe_only`；任何单个组件（poolHalt、quota_halt、NodeExhausted、dead）都不能「顺手」把 `probe_only` 清掉，反之亦然。所有解除/进入都走同一个 `quotaRouter` 锁与事件。

#### 8.2.2 矩阵

| 触发 / 组件 | T2 `poolHalt` | `quota_halt`（仅直连） | `NodeExhausted`（全局 5h） | `dead`（5min） | 新增 `(model,egress)` 排除 | `probe_only` | picker / sticky / manual |
|---|---|---|---|---|---|---|---|
| **FUL 429 on node E（NORMAL）** | 不改 | 不改（非直连） | **不 mark**（本次事故根因之一） | 不改 | 加/延长 `(M,E)`；`budget++`；`fresh++` | 达 K 且 60s 无 2xx → 进入；否则保持 NORMAL | `ExcludeEgress += E`；sticky 当前=E 时强制 `ForceSwitch` |
| **FUL 429 on node E（PROBE 当选）** | 不改 | 不改 | **不 mark** | 不改 | 延长 `(M,E)`；`budget++`；退避升级 | 保持 PROBE；`nextProbeAt=now+B` | 下一次探测优先复测冷却旧 IP，不选全新 IP |
| **FUL 429 on direct** | 不改 | `observeFailure`；达阈值 → halt 30s/恢复 2 次成功 | 不改 | 不改 | 不改（direct 不进 pair 表） | 不改 | 禁止探测 direct；`allow_direct_in_probe=false` |
| **403 FreeTier（T1）** | 8 个不同 fp/10min → halt 10min | 不改 | **confirm-then-mark**（T1 方案为准） | 不改 | 不改（403 不是配额 429） | 不改；poolHalt 生效时挂起 | 排除该 fp；手动 pick 仍受 poolHalt 限制 |
| **5xx / connect timeout（T3）** | 不改 | 仅 direct 计 | 不改 | **mark dead 5min** | 不改；不清已有 pair（配额状态不等于传输状态） | 若为探测：清 `probeInFlight`、退避升级、保持 PROBE | 换下一个候选；不触发 `fresh++` |
| **2xx** | 不改 | 每 2 次成功（≥60s 间隔）恢复 direct | 不改 | 不改 | **只清 `(M,E_success)`**；`fresh=0`；`lastSuccess=now` | 若为探测 2xx → **退出 PROBE** | 更新打分样本（真实 attempt，非 censored） |
| **`poolHalt` 生效** | — | 不调用 | 可继续 mark（403 路径） | 可继续 mark | 状态冻结、不新增 | **挂起**，禁止探测；`nextProbeAt` 顺延 | 所有请求 503；记录 `suppressed_by=pool_halt` |
| **`poolHalt` 解除** | — | — | — | — | — | 恢复；`nextProbeAt=max(now+5s, old)`；不清排除 | 允许选路；探测限额不变 |
| **`NodeExhausted` 标记** | 不改 | 不改 | — | — | **清掉该 node 的所有 `(M,E)` 排除**（避免 5h 后复活旧 pair） | 若所有候选都因它被排除 → 走 `all_excluded` fail-fast | picker 全局排除该 node，所有 model 生效 |
| **`NodeExhausted` 5h 到期** | 不改 | 不改 | 自动恢复（现逻辑） | — | 不自动清 pair（以 pair 自己的 TTL 为准） | 重新可探测 | 重新进入打分候选 |
| **`dead` 5min 到期** | 不改 | 不改 | — | 自动恢复 | **不清 pair**（dead 是传输，不是配额） | 重新可探测 | 重新进入候选 |
| **manual pick 选中被排除的 E** | 仍受 poolHalt | 若 direct 仍受 halt | 仍受 NodeExhausted | 仍受 dead | **允许一次 override**，但必须记 `suppressed_by=none, override=manual`；不 `fresh++` | manual 不进入 PROBE 逻辑；若 PROBE 中需 operator 显式 `force` | 记 `manual_override`，不改 sticky 评分；成功后清 `(M,E)` |
| **sticky 当前 = 被排除 E** | 不改 | 不改 | 不改 | 不改 | 不改 | 若 PROBE → 直接 fail-fast；否则 | **强制 `ForceSwitch`**，不返回被排除的 sticky；pick 失败 → `all_excluded` |
| **`ipBudget` 达 8/24h** | 不改 | 不改 | 不改 | 不改 | 该 E 硬排除 24h；`budget_exhausted` 告警 | 探测候选排除该 E；不可复测 | picker 排除 |
| **探测 timeout/5xx** | 不改 | 不改 | **不 mark** | 若 connect_error 则 dead 5min | 不改 | 清 `probeInFlight`；退避升级；保持 PROBE | 下一次探测换候选；不把超时当 FUL |

#### 8.2.3 与现有实现的冲突点（必须一起改，否则矩阵不成立）

1. **`main.go:3270-3276` 的 `drift.Halt` 分支**目前不记 suppressed、也不在发请求前拦；新设计必须把它前移到 `Admit`，否则「非探测请求打当前 IP」仍然存在。
2. **`main.go:3062 / 3549` 的 `shapeDriftObserveSuccess`** 会清整个 model 的 `seen`（T6 的 `resetLocked(true)`）；新设计只清成功的 `(M,E)`，不能清其它 egress，否则刚耗尽的节点会立刻被重试。
3. **`NodeExhausted` 的 5h mark** 目前由配额切换路径触发（T6 非 trial 分支 `main.go:3284-3285`）；新设计改为 confirm-then-mark（403 或切换后成功确认），429 本身不 mark。
4. **`quota_halt` 只观察直连**（`quota_halt.go`）；新设计保持，不把池内 429 喂给它，否则会与 pair 排除重复计数。
5. **`shapeDriftBlockedEgress` + `main.go:2971` 的 `all_egress_blocked`** 现在是「选到被排除的出口 → 503」；新设计在 `Admit` 就先判 `all_excluded`，并把 `would_be_egress` 填成候选（没有则为 null），避免「先选再拒」造成 sticky 污染。
6. **`egress.Get` 的直连回退**：池内节点全被 pair 排除 ≠ 池子没有健康节点。新设计必须区分 `no_node`（可回退直连，交给 quota_halt）与 `all_excluded_by_quota`（fail-fast，禁止直连）。
