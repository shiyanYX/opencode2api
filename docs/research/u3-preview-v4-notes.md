## 1. 三处搬迁的落点与版式决策

### 1.1 「节点来源」→ 节点页（选定：子视图，不折叠）

| 选项 | 为什么没选 / 选 |
| --- | --- |
| 放在设置页不动 | 用户已否决：来源是"节点从哪来"的数据源管理，不是"谁能用/坏了怎么退" |
| 节点页里做成**折叠区** | 5 张来源卡折叠后只看到一行标题：失败态需要"一眼从 5 张卡里指出哪张挂了"，折叠把这件事挡住了；且折叠区和方向切换条、统计格叠在同一屏，视觉层级会打架 |
| **节点页第二子视图**（选定） | ① 来源=**数据源配置**、健康=**运行状态**，是两类任务，不该抢同一屏；② 子视图能把整页宽度让给 5 张卡（≥820px 两列排布），失败卡的信息密度才放得下；③ 与日志页「分析/明细」用同一套子视图心智，全站一致；④ 切换成本仍是 1 次点击 |

页面顶部就是两个子视图按钮「节点状态 / 节点来源」，中间不夹任何东西；进「节点来源」后顶部出现预览态开关（落地删除）。

### 1.2 「日志级别」→ 日志页（选定：PageHeader 下一条 46px 薄条）

- 位置：`PageHeader`（标题/描述/时间窗）与「分析 / 明细」子视图之间，一条 `显示与排障` 薄条 —— **不抢主视图**：它只占一行，不动主内容宽度。
- 内容：`debug / info / warn` 三档分段控件 + 当前值徽章 + **"debug 会让日志量涨 5–10 倍，查完调回 info"** 的提示 + 「什么时候该开？」。
- **控件真的连着数据**：切到 `debug` 后，明细里展开任意一条会多出「请求体摘要（4KB）」这一行；这条被写进了 verify 断言（`debug` 态必须 `[data-debug-only] >= 1`，其它态必须 0），不是画个控件摆着。
- 为什么不上移到全局设置：日志级别只影响日志量与排障细节，用户是"翻日志时发现没有 debug"才想起来调，就地可调最短路径。

### 1.3 设置页（v4）删干净了吗

| 检查 | 结果 |
| --- | --- |
| 可编辑控件 | **恰好 5 个**：`api_key` / `cooldown_exhausted` / `cooldown_dead` / `max_switches` / `health_interval`（verify 用集合相等断言，不是"数量等于 5"） |
| 「节点来源」整组 | 0 命中：无 `[data-ctl=subscriptions]`、无 `[data-ctl=webshare]`、无 `#subRows` / `#wsRows` / `.subcol`、无「添加订阅源 / 保存并重建节点池 / 手动添加节点」按钮 |
| 「日志级别」 | 0 命中：无 `[data-ctl=log_level]`、无 `#log_level`、无 `#seg_log_level` |
| 只读诊断 | 6 条，每条都带「只读 · 改请改配置文件」，容器内 **0 个** input/select/textarea |
| 危险区 | 4 个按钮，二次确认（`danger` 态必须弹窗，其它态不许弹） |
| 搬走后的去向提示 | 每个方案底部一条「已搬走：节点来源 → 节点池页；日志级别 → 日志页」，避免用户以为设置项凭空消失 |

> **建议（只提，不自行搬）**：`health_interval`（体检间隔）语义上更像节点行为，跟「节点来源」一起搬去节点页也说得通。但用户只说搬节点来源，本版**留在设置页**并在那里叫「体检间隔」；若后续要搬，设置页就只剩 4 个控件（接入 1 + 失败行为 3），可以并成一张卡。

### 2.4 数据真实性声明（不造数）

- Panel 1–6 的每个数字都是本轮从生产 `/data/call_log.jsonl`（233,452 条）算出来的：分位、按天/小时、按模型/节点/错误、尝试次数分布、各段耗时均值。复算命令见 `docs/research/u3-logs-redesign.md` §3.5。
- **两处近似已在页面里标注**：① 按小时柱的 ok/fail 拆分是按当天成功率（80.7%）折算（接口只给总数，真实实现应有逐小时 ok/fail）；② 各段耗时里"生成 + 重试空转 + 排队"在线上日志里没有独立字段，只能取 `duration_ms − ttft_ms − dial_ms` 均值，页面上写的是"三段相加 ≠ 总耗时，差额是重试空转 + 排队"。
- 明细表 24 条是**样例**（按生产画像配比），页脚与明细底部都写了"预览只放 24 条样例；真实实现按 before 游标继续加载"。

## 3. `nodes-v3.html`：节点健康 3 方向 + 节点来源

### 3.1 三个方向的一句话差异

| 方向 | 一句话 | 1440 页高 |
| --- | --- | --- |
| ① 表格 | 一屏看全部节点，冷却/故障排最前，列多但信息全 | 1003 px（1.11 屏） |

| ③ 卡片 | 一条节点一张卡，手机上最好读；桌面一屏 9 张 | 1126 px（1.25 屏） |

### 3.2 「节点来源」区块

- 5 张卡：**飞鸟云 34 / 红杏 63 / Webshare 1: 100 / Webshare 2: 10 / Webshare 3: 10 = 217**（本轮修完两个 bug 后的真实贡献数，不是编的）。
- 每张卡都有：源名 + 类型（订阅/Webshare）+ **脱敏地址或 key（点一下可展开）** + 更新间隔（24h）+ 上次更新 + 下次到期 + **该源当前贡献节点数** + 状态（正常 / 拉取失败 / 返回 0 节点）+ **失败原因** + 操作（手动刷新 / 编辑 / 删除）+ 顶部「+ 新增来源」。
- 状态**冗余编码**：`●` 正常 / `○` 返回 0 节点 / `✕` 拉取失败，每个都带符号 + 文字 + 边框色（`.is-fail` 红框、`.is-zero` 黄框），不只靠颜色。
- 三个预览态（落地删除）：
  1. **全部正常** —— 5 源共 217 节点；
  2. **红杏拉取失败** —— 该卡红框 + 「最近错误：HTTP 403（订阅 token 可能过期）」+ 「仍在上次成功拉到的 63 个节点」标记（`上次成功的结果`）；底部说明「其它 4 个源正常，节点池仍有 154 个可用节点，不影响服务」；
  3. **所有来源为空** —— 5 张卡全部 `返回 0 节点`，底部说明"这时节点池为空，请求退化到直连或直接失败"，并区分"解析问题 vs key 问题"。
- 空态：若来源列表为空，显示「还没有任何节点来源」+ 引导（`+ 新增来源`）。

### 3.3 与节点健康的关系

「节点来源」不是隔开的另一个页面，而是同一页的第二个子视图：来源出问题时节点数会立刻反映在「节点状态」里，两边切换着看就能判断"是我的源挂了，还是上游节点挂了"。

### 5.1 一处 flake 的处置（如实记录）

第一次全量跑出现 `logs-v2.html` 1 个态失败：`CLICK_FAILED #themeBtn: Timeout 2500ms`。单独重跑该文件 **63/63 通过** ⇒ 判定为连跑 260 态时机器负载导致的点击超时，不是页面问题。已把 `page.click` 超时从 2.5s 提到 6s，重跑全量 **260/260**。

## 6. 待拍板 / 风险

1. **明细选 A 还是 B**（用户还没选）：A 行内展开适合"连续对比多条链路"，B 抽屉适合"只看一条、不要列表跳"。我倾向 **A**，因为排障时经常要上下对比两次尝试。

3. **体检间隔（`health_interval`）是否也搬到节点页**：只提建议，未自行搬（见 §1.3 末尾）。
4. **节点来源的"更新间隔"是否要就地可编辑**：目前卡上是只读展示（24h），编辑走「编辑」按钮；如果用户经常按源调间隔，可以像日志级别那样做成就地分段控件。
