### 2.1 两种失败形态的原始报文（这决定了降级方案怎么判）

**形态① 410 —— 有机器可读提示（20:16:15 起）**

```json
{"type":"error",
 "error":{"type":"ModelDeprecated",
          "message":"Model space-bunny-free has been deprecated. Use minimax-m3.1-flash-free instead."},
 "metadata":{"model":"space-bunny-free","replacement":"minimax-m3.1-flash-free"}}
```

**形态② 400 —— 只有一句人话，没有结构化提示（20:30:09 起，676 条）**

```json
{"error":{"type":"server_error","message":"Upstream request failed: Model is unavailable."}}
```

> ⚠️ 注意形态②的 `error.type` 是 `server_error`，**不是** `model_not_found`。
> 唯一能判定的信息是 message 里的 `"Model is unavailable."` —— 所以降级检测必须同时支持
> 「看 410 的结构化 type」和「看 400 的 message 文本」，且两者的置信度不同。

顺带发现：窗口内还有**两种形近但无关**的 400，不能误判成模型下架 ——
`ModelProtocolUnsupported`（协议不支持）与 `cache_control 参数不支持`。
另外 `404 {"error":{"type":"server_error","message":"Upstream request failed: Endpoint is unavailable."}}`
说的是 **Endpoint** 而不是 model，也不能当成模型下架。

### 2.3 为什么客户端会退化成裸名（代码级，这是「与我们无关」不成立的原因）

`resolveModel`（`main.go:1412` `resolveModelWithDocs`）对裸名做 `-free` 反查，但用的是
**上游目录**（`modelExistsInCaches`）而不是命名约定：

```go
if m != "" && !isFreeModelIn(docs, m) {
    freeID := m + "-free"
    if modelExistsInCaches(freeID) {   // ← 目录里没有 space-bunny-free 了，这里永远 false
        return freeID
    }
}
return m                              // ← 于是裸名被原样发给上游 ⇒ 400 Model is unavailable
```

⇒ 上游一删目录，**裸名这条路就永久断了**，且错误形态从「有提示的 410」退化成「没提示的 400」。
这是我在 task-21 报告 §3.4 第 6 点已经记过的**独立路由 bug**（当时针对 `mimo-v2.5`），

> 走的是 `isFreeModelIn(docs, m)` 这条正常路径，反查根本不会被执行。
> 所以按用户裁决「使用下架模型是配置的问题」——修它等于**替配置过期的用户兜底**，
> 属于 §6.3「不做」的范围。此处的代码事实保留，是为了解释「为什么错误形态会从 410 变 400、
> 为什么客户端自己改回来也没用」，不是主张要去修它。

## 4. 根因

三层叠加，缺一不可：

1. **上游侧（触发）**：`space-bunny-free` 于 20:16:15 被标记 deprecated（410 + replacement），
   并从免费目录移除。
2. **网关侧（放大）**：`shouldRetryUpstreamStatus`（`main.go:2691`）只重试 401/429/502/503/504，
   **410 与 400 都不重试**，也**没有任何「换模型」能力** ⇒ 这类错误直接透传给客户端，
   一次都不尝试自救。
3. **路由侧（恶化）**：裸名 `space-bunny` 的 `-free` 反查依赖上游目录（§2.3），
   目录一删就永久失效 ⇒ 原始报文从「有 `replacement` 提示的 410」
   退化成「只有一句人话的 400」，连人工排查都要翻日志才知道该换哪个模型。

**告警为什么沉默**：`nodeAlerts.recordNodeAttempt(nodeFp != "", err == nil)`
（`main.go:2839` 非流式 / `main.go:3240` 流式）——C-5 的样本是**传输层**成败。
400 意味着上游正常回了 HTTP 响应 ⇒ `err == nil` ⇒ 记为节点**成功**。
注释里写得很清楚：「拿到任何上游响应（含 403/429）都说明这条出口是通的」。
所以 11 小时里节点层指标是 100% 健康的，C-5 按自己的定义**正确地**保持了沉默。

⇒ **这不是 C-5 的 bug，是「可观测性只覆盖了传输层，没有覆盖『模型可用性』这一层」。**

### 5.3 为什么这是「最危险的耦合」

- 第一批口径下，这场事故在面板上是**刺眼的**：`成功率 3.22%`、`space-bunny` 那一行 727 条全红。
- 第二批上线后，同样的数据变成 `成功率 50.00%` / 模型表里连 `space-bunny` 都不再出现；
  纯事故段更是**整段消失**。
- 更糟的是它和 task-21 的**设计意图正好相反**：task-21 想剔除的是
  「客户端传了个我们根本不提供的野名字」（如 `mimo-v2.5`、`claude-opus-4-5`），
  而 `space-bunny` 是**我们曾经正式提供过、客户端一直在正常使用**的模型 —— 它是**故障**，不是噪声。
  两者在判据上无法区分（都不在 docs、都不是 `-free` 结尾）。

⇒ **第二批单独上线 = 把「模型目录漂移」这类最危险的故障，从「失败率飙升」伪装成「未映射噪声」。**
我的建议是「先有配套可观测性（§6 B）再上线第二批」，**Lead 已据此暂缓第二批**。
此后用户对整条模型线给出最终裁决「不修」（§6.0），并给出新口径（§5.4）——
**这个耦合没有被加可观测性去堵，而是被用户显式选择为正式语义**，所以它不再是「待修风险」。

### 6.1 A. 自动降级 —— 已否决（**不建议现在做**）

**技术上本来是可行的**，而且上游主动给了提示（这是本次事故最有价值的背景知识，值得长期记住）：

- **410 形态带机器可读的替代建议**（20:16:15 首次出现）：
  ```json
  {"error":{"type":"ModelDeprecated","message":"Model space-bunny-free has been deprecated. Use minimax-m3.1-flash-free instead."},
   "metadata":{"model":"space-bunny-free","replacement":"minimax-m3.1-flash-free"}}
  ```
  `metadata.replacement` 是**上游指定的替代模型**，比我们自己猜一个准得多。
- **400 形态没有提示**（20:30 起 674 条）：`{"error":{"type":"server_error","message":"Upstream request failed: Model is unavailable."}}`
  —— 连 `error.type` 都是 `server_error`，只能靠 message 文本判定。
- 所以「自动降级」在数据上是**做得到**的，否决不是技术原因。

**为什么不做**（用户裁决，我认同）：

1. **会静默改写用户意图。** 用户点名要 `space-bunny`，我们替他换成 `mimo-v2.6-flash-free` ——
   模型能力、上下文长度、输出风格、工具调用行为都可能不同。对 agent/自动化调用方，
   这是在用户不知情的情况下改变了他的程序行为，比报错更危险（**报错至少是可观测的**）。
2. **客户端无从感知。** 除非客户端专门读我们加的响应头，否则它以为自己拿到的是 `space-bunny`。
3. **会掩盖配置漂移。** 一旦自动降级，用户永远不会去改自己的配置，过期的模型名会长期寄存在
   我们的降级路径上，把一个「该修的配置问题」变成「网关永久的隐性负担」。
4. **责任边界应当清晰。** 上游下架模型是调用方配置与上游之间的事；网关擅自替换，
   等于替用户承担了他该做的决策。

> 若将来真要重新考虑，必须先回答（本次不实现，仅留档）：**replacement 指向的模型本身也不可用怎么办？**
> 且必须用「每次请求最多降级 1 次 + 降级目标必须来自当前免费目录 + 降级目标失败后不再二次降级、
> 直接返回原始错误」三重限制防死循环；并在 call_log 记 `degraded_from` / `degraded_to` /
> `degrade_reason`，回 `X-Degraded-From/To` 响应头。**另一条相关方案「模型别名自动注入」同样否决**：
> 事故当天的人工别名止血是对的（人工决策、可回溯），自动化会把「猜错替代模型」的错误扩散到
> 所有使用该别名的客户端。

### 6.2 B. 模型名失效可观测 —— **可选建议，不在本批排期**

**目的重新定位**：不是替用户修配置，而是**帮用户发现自己的配置过期了**。
但请注意：**这件事不是必须现在做**，理由见 §6.2.1。

设计原则：**只读**。不改写请求、不替换模型、不改判据公式 B、不动 `node_alert.go` 与 `proxy_node.go`。

#### 6.2.1 为什么可以不做：现有面板已经能照出来

`task-21` / `task-22` 上线后，概览页已经有一行「**未映射模型请求 N 次**」+ 按模型展开。
本次事故的裸名 `space-bunny`（727 次、0 成功）**正好落在这一行的口径里**，不会被完全隐藏 ——
也就是说，最坏情况下用户至少能在面板上看到「有个模型名在一直失败」。

原 `task-38`（把它升级成「结构化 ERROR + 超阈值横幅」）**已由 Lead 从任务板撤掉**；
是否升级、升到什么程度，留给用户后续决定，本批不排期。

> 08:30 的新口径（§5.4）让 B 的必要性**更低**而不是更高：按「曾经成功过」判据，
> **真正危险的形态（已经在我们这里成功跑过、后来被上游下架）仍然算 mapped**，
> 它下架后的失败会照常推高成功率分母里的失败数 ⇒ 概览会**自己亮红灯**，
> 根本不需要额外的漂移告警。会被排除的只有「从来没成功过的名字」——
> 那正是用户说的「配置问题、不用修」。

#### 6.2.2 若将来要做，最小增量是「只读分类」

单靠名字无法区分「上游下架的模型」与「客户端拼错的名字」（这正是 §5 那层耦合的来源）。
但**加一个只读的历史成功判据就能区分**，且不需要改公式 B ——
对每个「当前不在免费目录、且不以 `-free` 结尾」的名字 `U`，查已有的两个小时桶：

- `bucketOK[U]` —— `U` 自己成功过几次
- `bucketOK[U+"-free"]` —— 它的 `-free` 孪生成功过几次

| 判定 | 条件 | 面板文案 | 含义 |
| --- | --- | --- | --- |
| `retired`（疑似下架） | 两者之和 > 0 | 「**曾经可用，现已从上游消失**」 | 用户配置过期了，**改个模型名就能恢复** |
| `unknown`（疑似配错） | 两者皆 0 | 「**从未成功过，疑似模型名写错**」 | 拼写错误 / 用了别家服务商的模型名 |
| `active` | 在免费目录里 | 不显示 | 正常 |

实证（生产 232,976 条，窗口=全量）：

| 模型 | 自身 OK | `-free` 孪生 OK | 分类 | 与实际相符？ |
| --- | ---: | ---: | --- | --- |
| `space-bunny` | 0 | **31,154**（`space-bunny-free`） | **retired** | ✅ 确实是上游下架 |
| `mimo-v2.5` | 0 | 166,518（`mimo-v2.5-free`） | retired | ✅ 其 `-free` 版本 10-07 起 410 |
| `x-preview-f` | 0 | 1,265（`x-preview-f-free`） | retired | ✅ 上游已摘掉 |
| `claude-opus-4-5` | 0 | 0 | **unknown** | ✅ 我们从来没提供过这个模型 |
| `gpt-4o-mini` | 0 | 0 | **unknown** | ✅ 同上 |
| `hy3` | 0 | **1**（`hy3-free`，2026-08-22 唯一一次 200） | **retired**（勉强） | ⚠️ 见下方局限 |

数据来源全部是**已有的**（无需新持久化）：`call_log` 小时桶（`hourBuckets` + `unmappedBuckets`）、
`freeModelDocsCache`（与 `/api/models` 同源、已有 1 小时刷新）、桶里的 `OK` 计数。

> **这套判据的局限（实测发现，不隐瞒）**：`hy3` 是个反例 —— 它自己那 2 条是 **401**（不是 400），
> 本来不是目录漂移；但历史上 `hy3-free` 曾成功过 1 次，于是它会被标成 `retired`。
> 也就是说这个标签的准确语义是「**我们曾经成功服务过这个名字（或它的 `-free` 孪生）**」，
> 而不是「上游刚刚下架了它」。它足以回答用户最关心的那个问题（「我是不是配了个早就没的模型名」），
> 但**不能拿它当精确的下架时刻**。若将来要求更准，需要额外的 `first_seen_unmapped_at` 与
> 「最后一次成功距今多久」两个维度，那就超出「只读小增量」的范围了。

#### 6.2.3 若真要落地，先过这四道闸

1. **字段形状必须先经 Lead 批准。** 任何给 `/api/stats` 的 `unmapped_requests` 加字段
   （例如 `share` / `last_hour_count` / `drift[]`）都是**对外契约变更**，必须先约定
   「旧后端 / 新面板」与「新后端 / 旧面板」两个方向的兼容：缺字段一律显示「—」，
   绝不允许显示 0 或 NaN。
2. **面板侧要等 UI 大改（U3）定稿后再做**，避免二次改版；告警横幅的元素 id 必须与
   `#nodeAlert` 区分，且**不得新开轮询**（沿用既有刷新节奏）。
3. **阈值（若做）**：`count >= 20 || share >= 5%`；`count == 0` 永不告警；
   日志侧用**聚合后**的结构化 ERROR（单条 `upstream error` 是噪声，运维不会去数 ——
   本次事故日志里其实有 674 条 `upstream error`，但没有一条是「有人在拿一个不存在的模型」的聚合信号）。
4. **必须独立验收**：涉及统计口径的展示，算错了比不显示更糟；验收须含变异测试
   （改小阈值必须红、去掉 `kind` 必须红、伪造 `last_ok_at` 必须红）。
