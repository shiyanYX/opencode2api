## 概念对照：**自动映射**（已有）vs **自动路由**（未上线，本文件 §10/§11 为其预留）

> 这两个词长得像、做的事完全不同 —— 用户明确说过「**我说的自动映射模型是 auto 路由，不是现在已经有的自动映射免费模型**」，所以先钉在这张表里，后面所有讨论都以它为准。

| | **自动映射**（今天就有，在跑） | **自动路由**（本版不实现，只预留） |
| --- | --- | --- |
| 一句话 | **静态一对一**：客户端名 → 一个固定的真实模型 | **动态多选一**：逻辑模型名 → 一组候选真实模型 → 每次请求挑一个 |
| 依据 | 配置里写死的映射表（`model_alias` + `-free` 后缀约定 + 改名/隐藏表） | 每次请求时按统计/延迟/成本/优先级**现算** |
| 什么时候决定 | 请求进来时查表，**同一名字永远同一结果** | 请求进来时在候选组里挑，**同一名字每次可能不同** |
| 失败时会怎样 | 这个名字对应的模型失败 ⇒ 请求失败（**换的是节点，不是模型**） | 候选组里还有别的模型 ⇒ 可以换模型（**是否允许同请求内换，待商讨**） |
| 用户能感知到什么 | 无（客户端名不变，上游模型不变） | 必须可感知：响应头/体里写实际用了谁，日志记一条路由决策 |
| 谁定义 | 系统 + 用户的映射表 | **只能用户自己定义**：逻辑名 + 候选组（红线，见 §11.6） |
| 相关代码 | `resolveModelWithDocs`（`main.go:1408-1457`）、`model_alias`（`main.go:1030/1285/7058/7136`） | 无（不存在），预留点见 §11.2 |
| 在本预览里的位置 | 模型页第 1 张卡「模型叫什么（映射表）」 | 模型页第 2 张卡「模型自动路由（未上线）」 |

> ⚠️ 常见混淆：把「自动映射免费模型」说成"auto 路由"。**不是** —— 前者是查表，后者是选择；前者失败只能换节点，后者才可以换模型。

## 0. 结论速览

| 问题 | 结论 |
| --- | --- |
| 两版为什么都不满意（一句话） | **两版是同一批 29 个控件的两种分组**（原型自己的注释就写着「两套方案放的是同一批控件，区别只在怎么分组」），换的是标题不是形态；而且两版都还是「**把配置文件字段搬到网页上**」。用户否的是形态，不是分组名。 |

| 最重的三个建议 | ① **节点来源 3 项（订阅源/Webshare/手动节点）搬去「节点池」页** —— 它们保存时会**同步重建池子**（`main.go:7309-7336`），本质是节点运维不是"设置" ② `quota_error_signals`（额度判定关键词）**从可编辑降级为只读**（改错会引发误判风暴） ③ 配置页只留 **12 项**（15 项 − 3 项搬走），其余 5 项后端字段**仅配置文件**、10 项模型类**单开模型页** |
| 三个方向（结构上真不同） | ① 单页 + 任务向导 + **即时生效/撤销** ② 拆 3 页（连接/路由/维护）+ 每卡即时生效 + 人话 ③ 单页 + 工程参数表 + **整页一次提交**（专家向对照） |

### 1.3 线上现状（只记录，本轮不改）

- 配置分散在现有 5 个页面的**其中 3 个**：`#page-subs`（订阅与配额，768-782 行附近）、`#page-misc`（代理与模型，791-824 行）、`#page-logs`（日志级别，852 行）；5 个页面 id：`page-overview` / `page-nodes` / `page-subs` / `page-misc` / `page-logs`。

- **25 项全部热生效、无需重启**，但分两类：
  - **22 项**走 `POST /api/config`：合并补丁 → `saveConfig` → `applyConfig`（`main.go:1282`，同步更新别名表/密钥/出口客户端/冷却与探针参数，`egress.Configure` 在 `:1322`）

### 5.4 原推荐：**方向 ①（任务向导单页 + 即时生效 + 撤销）** —— ⚠️ 用户 2026-10-20 选了 **方向 ②**，本小节作为已否决方案的记录保留

1. **体量已经变小**：模型 10 项去了模型页、节点来源 3 项去了节点池页，配置页只剩 **12 项**（桌面约 1.2 屏）—— 这时"拆页"（方向 ②）只会增加跳转成本，收益反而下降；

4. 危险区放到页尾独立卡片，清数据/断服务不再和密钥同屏。
保留方向 ③ 的价值：它是**工程视图**的备选 —— 将来若用户想要"一次改一批、最后统一提交"，可以直接加一个「工程模式」开关复用 ③ 的表格。

## 9. 打磨方案对照（A1–A7：每条给候选 / 理由 / 取舍 / 最终选择）

### A1 三页命名与顺序 → **连接 / 自动切换 / 日志与维护**（+ 模型页单开）

| 候选 | 命名 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 1（旧） | 连接 / 路由 / 维护 | 短 | 「路由」「维护」是行话，小白不知道点进去有什么 |
| 2（**选中**） | **连接 / 自动切换 / 日志与维护** | 望文生义：「自动切换」= 出事了系统自己换；「日志与维护」= 排障与清数据 | 3 个字以上的页签名在 320 上要缩到 11.5px |
| 3 | 接入 / 容错 / 日志 | 更短 | 「容错」同样不是人话 |

**顺序理由**：按"第一次把它用起来"的动线排 —— ① 连接（唯一必须配的）→ ② 自动切换（默认值就能用，想调再进来）→ ③ 日志与维护（排障 + 危险区，不该是日常入口）。
**模型页为什么单开**：它不是"配置行为"而是"模型清单"，改错影响面大、不常改，所以放最右并加「单开」徽标。
**取舍**：把「路由」改叫「自动切换」后，将来要做"选哪个节点"的策略时缺一个上位词 —— 解决方式是在**页内**用「节点不好用时」当卡名 + 「智能路由（未上线）」卡承载策略，不再改页名（改名成本高于收益）。

### A2 移动端页签形态 → **分段控件（等宽按钮行）**

| 候选 | 390/320 表现 | 取舍 |
| --- | --- | --- |
| 横滚 tab | 4 项时第 4 项（模型）经常在屏幕外，可发现性差 | 否决 |
| 下拉 `<select>` | 省高度，但多一次点击、看不出"只有 4 页" | 否决 |
| **分段控件（选中）** | 4 个按钮在 320 一行放得下（实测 320 无横向滚动） | 页签变矮（320 上 40px 高、11.5px 字），可点区仍 ≥32px |

**取舍**：如果将来加第 5 个页签，320 一行放不下，就得回退成横滚或两行 —— 这条写进落地注意。

### A3 「改即生效 + 撤销」在分区页怎么落 → **固定底部撤销条**

| 候选 | 说明 | 结论 |
| --- | --- | --- |
| 每卡「保存」按钮 | 与现状（热生效、无保存按钮）冲突，制造"没保存"焦虑 | 否决 |
| 顶部 toast | 会盖住卡头（正在改的那张卡） | 否决 |
| **底部固定撤销条（选中）** | 不遮卡头、不改文档流（不引起 reflow） | 采用 |

- **位置**：`position:fixed` 底部居中，`max-width: calc(100vw - 24px)`。
- **生命周期**：3 秒自动消失（`setTimeout`），`×` 手动关；**切换页签后仍然在**（它挂在 shell 上，不属于某一页）—— 实测 `390x844|undo` 状态里点完 seg 再切页，撤销条仍在。
- **撤销语义**：预览里回滚内存 UI；落地 = 用旧值再发一次 `POST /api/config`（PATCH 语义，**不是事务**，中间态可能被别的请求看到）。
- **危险操作与撤销条的关系**：危险区 5 个按钮**不出现撤销条**，只走 `confirm` 二次确认，文案里写「不可撤销」。给不可逆操作配"撤销"是欺骗。
- **不可撤销清单**：清空 Token 统计 / 清空调用日志（连带清零统计）/ 解除全部节点标记 / 退出登录（会话失效）/ 刷新会话&模型（只影响内存态，可重来但不可撤销）。

### A4 60 秒阻塞怎么写、超时怎么办

- **位置（选中）**：迁移卡上内联一枚「保存会重建节点池 · 最长 60 秒」徽标 + 一句话，细节收在卡内 `<details>`（默认折叠，不撑长页面）。否决"每次保存前弹 modal"（会烦）与"只写在小字里"（会漏看）。
- **人话文案**：「保存它们不是改个开关，服务器会立刻重拉订阅、重建整个节点池，最长 60 秒；期间新请求可能失败或变慢。」
- **超时（>60s）三步**：① 配置**已经写入**（先落盘再重建），转圈只是重建没结束 —— 不要重复点保存；② 去节点池页点「重新加载订阅」，节点数若为 0 就是订阅地址/代理 key 填错；③ 连续两次失败 → 把「最近错误」贴给管理员。
- **落地建议**：真正阻塞时页面顶部出现进度条（"正在重建节点池…"），重建结束自动消失；**"最长 60 秒"是承诺，若实测 p95 > 60s 必须改文案**（去掉数字或写区间），别让 UI 说谎。

## 10. 为「自动路由」预留（节点自动选择；本版不实现）

> 出处：`ROADMAP.md` §「2b · 打分系统（设计已收敛，尚未实施）」（约 :853-905），**不自己重新设计路由**。

### 10.1 那节的核心（照抄，不改数值）

- **统计只做「选择器」，不做「触发器」**：只有两种情况会换节点 —— ①连续失败、②配额耗尽 / 探测判死；统计**从不主动触发换节点**，它只在"已经被迫要换的那一刻"给候选排序。
- **两种故障分开算**：连不上 ≈ **95 秒/次 ⇒ 忍 1 次就换**；普通失败 ≈ **11 秒/次 ⇒ 可忍 2~3 次**。
- **排序信号**：成功率（请求级口径，中位 90.61%；事件级 74.05% 不适合排序），窗口 **最近 24h** 最好（95.4%）。
- **候选集为空时的兜底**：回退到插入顺序（否则退化成随机挑）。
- ⚠️ ROADMAP 明确写了：**现状"第一次连不上就立刻换"是正确的，不能改坏** —— 所以"连不上容忍次数"的默认值 1 = 现状，不是新行为。

### 10.2 节点选择策略：三个方案并列，**待商讨**（预览里不做选择器）

用户原话：「是否固定一个节点出还有待商讨」。→ 预览的「智能路由（未上线）」卡里做成**三张对比小卡**（不是可切换 tab，避免暗示已定），三个都带「待商讨」徽标，且**不替用户选**：

| | A 随时自动换（≈ 现在） | B 固定一个节点直到失败（粘住） | C 会话内固定（折中） |
| --- | --- | --- | --- |
| 适用场景 | 节点多、坏节点也多，想尽快绕开问题节点 | 想让同一客户端长期走同一条线路，行为可预期 | 既要缓存命中，又不想被单个坏节点卡死 |
| 代价 | 一个请求可能连换几个节点，延迟叠加；对单节点质量不敏感 | 选中的节点当时不好就一直难受；需要"手动换一个"的出口 | 要定义"会话"（客户端没统一标准），实现最复杂 |
| 对**配额冷却** | 坏节点很快被标冷却，池子"看起来"健康度下降更快 | 冷却节点不会被反复撞，但池子利用率低（一个节点扛一个会话） | 介于 A/B 之间：失败才换 |
| 对**缓存命中率** | 同一会话多次换节点 ⇒ 上游提示词缓存容易失效（缓存按节点/账号维度算） | **最好**：会话越稳定，上游缓存复用越多 | **较好**：会话内不换、跨会话才换 |

> 缓存命中率与"换节点频率"强相关 —— 这也是为什么策略必须和缓存指标一起定。

### 10.3 未来字段表（本版不实现；每个字段将来落在哪页哪个卡）

| 字段（建议名） | 含义 | 默认值 | 将来落点 | 与现有 25 项的关系 |
| --- | --- | --- | --- | --- |

| `route_strategy` | 选择策略：A 随时换 / B 固定直到失败 / C 会话内固定 | 待定（未拍板） | 自动切换页 →「智能路由」卡顶部 | **新增**；B/C 会**部分吸收**现有的 `socks5_sticky`（会话固定出口）—— 但那层是"出口节点"，见 §10.5 |

### 10.4 与现有 25 项的关系（一句话结论）

- **保留、不替代**：`auto_switch` / `max_quota_node_switches` / `exhausted_cooldown_hours` / 健康检查间隔 —— 它们是"要不要换、什么时候能回来"，路由策略是"换给谁"。
- **新增**：`route_enabled`、`route_strategy`、`retry_normal`、`rank_prefer`、`node_allow_deny`。
- **复用**：`region_prefer` → 现有 `model_region_map`。
- **不变**：连不上的容忍次数默认 1（= 现状，ROADMAP 要求别改坏）。

### 10.5 两层不要混：节点层 vs 模型层（task-50 会展开）

```
请求(claude-sonnet-4)
  ├─ 模型层：逻辑模型 → 候选组 → 选一个真实模型   ← 未来「模型自动路由」（task-50 / notes §11）
```

两层**正交**：失败时换的东西不同（换模型 vs 换节点），日志必须能分别归因；粘性也是两层的（`socks5_sticky` 粘出口，模型粘性是另一套）。

### 11.3 今天的失败重试：**换节点，不换模型**（已逐行确认）

- 两条上游调用路径各有一个 `for attempt` 循环：非流式 `callOpenCodeAPI`（`main.go:2771` 起，循环 `main.go:2838`）、流式（`main.go:3172` 起，循环 `main.go:3244`）。
- 循环里**唯一会变的是节点**：`nodeSwitchPending` → `egress.Get(EgressRequest{ForceSwitch: nodeSwitchPending})`（`main.go:2847`、`main.go:3021/3049/3069/3092` 等处置位）。
- `modelID` 是**函数入参**，两条路径全程**没有任何重新赋值**（全仓 `grep "modelID = "` 零命中）⇒ **同一请求内不会换模型**。
- 循环上限 = 重试上限 + 配额切换预算（`loopBudget := maxAttempts + maxQuotaSwitches`，`main.go:2836`）；墙钟预算 `upstreamLoopBudget = 120s`（`main.go:2768`），**只做收手、不打断在途响应**。
- 流式还有一条硬约束（代码注释原文）：**「流式：仅头部非 2xx 时可切；已吐字节不可重试」** ⇒ 流一旦开始，模型/节点都不能换。

**⇒ 这就是"为之后预留"的关键缺口**：现在"一个名字 = 一个模型"，模型层是完全静态的；节点层才有动态选择。auto 路由要动的正是 `modelID` 这一层。

### 11.6 「失败处理」为什么是待商讨项（代价要写清）

| 选择 | 好处 | 代价（必须写进文档，别只写好处） |
| --- | --- | --- |
| **仅影响下一次请求**（推荐默认） | 语义干净：一次请求 = 一个模型，`finish_reason`/usage/流式增量都只有一个来源；实现简单 | 这一次失败就是失败（但对客户端是"立刻换下次"，感知上是可接受的） |
| 同一请求内换模型重试 | 命中率高一点 | ① **响应风格突变**（同一段对话前后两个模型写的，用户能看出来）② **缓存失效**：上游 prompt cache 按模型算，换模型等于全量重算 ③ **`finish_reason` 与 usage 归属复杂**（一次请求两个模型的 token 怎么记账？）④ **流式已开始 ⇒ 物理上不能换**（见 §11.3 硬约束）⑤ 与现有"换节点重试"叠加会变成二维重试矩阵，预算难控 |

> 结论：**默认 `仅影响下一次`**；同请求内换模型即使要做，也只能在"尚未向客户端吐任何字节"的窗口内做，并且必须在日志里记 `route_candidates_tried`。

### 11.7 两层正交（UI 与日志都必须能分开归因）

```
请求(claude-sonnet-4)
  ├─ 模型层：逻辑模型 → 候选组 → 选一个真实模型      ← 「模型自动路由」（本节，未上线）
  └─ 节点层：该真实模型 → 节点池 → 选一个出口节点     ← 「节点自动选择」（§10，未上线）
```

- 两层换的东西不同：模型层失败换**模型**，节点层失败换**节点**；
- 两层的粘性也是两层：`socks5_sticky`/会话固定出口 ≠ `sticky_model` 会话固定模型；
- 日志必须分别归因：节点换了几次（现有 `switch` 事件）+ 模型挑了几次（新增路由决策事件），否则"这次为什么慢/为什么答案风格变了"永远查不出来；
- **顺序**：先模型层选定真实模型 → 再由节点层为这个模型选出口（节点还带区域约束 `model_region_map`，换模型可能连区域偏好都要重算）。

### 11.8 红线（写死，不许越）

1. **只在用户自己定义的候选组里挑**。不许替"用户没定义过的名字"猜一个模型顶上 —— 那正是 `space-bunny` 那次事故后被用户否决的「自动降级/模型替身」。
2. **不许静默替换**：每次挑了谁、为什么（依据与分值）、落选的是谁，都要可查（`expose_model` 必须默认开）。
3. **措辞只用「路由」**：UI 与文档都不出现「自动降级 / 兜底 / 替身」（预览已加断言 `no_fallback_wording`）。
4. **不许绕开免费额度**：候选组里每个候选都必须先通过免费表校验。
5. **不许默认开**：`router_enabled` 默认关、逻辑模型没定义时行为与本版完全一致。
6. 没有用户定义 ⇒ **不做任何推断**，请求该失败就失败（失败信息要能看懂）。

- ① 的 1440 内容区 1.10 屏——「8 控件 + 2 张表 + 只读折叠」在 900 px 视口下**略超一屏**（多出 0.10 屏）。要压到 1.0 屏只能把两张表改成"点开才显示"（等于加抽屉，与①的定义冲突），所以如实报 1.10。
- ② 打开全部折叠 = 1.25 屏（`acc` 态实测 1123 px）；只读诊断展开 +0.57 屏。
- ③ 单组内容 0.33 屏，意味着**大量空白**——这是双栏在 8 控件规模下的天然代价（见 12.5 缺点）。

步数 = 到控件所需点击次数 + 1 次编辑动作（表格新增连填两格算 1 步，因为同一屏）；滚屏 = 控件位置 ÷ 视口高。

### 12.4 只读诊断与危险区在各案的位置

| | 只读诊断（6 项，标「只读 · 改请改配置文件」） | 危险区（4 个不可撤销操作） |
| --- | --- | --- |
| ① | 「排障」卡内，**默认折叠**的 `<details>`，标题就写「展开看当前生效的 6 个只读值（改请改配置文件）」 | 最后一张卡，**始终可见**（不折叠，避免误点也避免找不到） |
| ② | 「排障」组（默认折叠）→ 组内再折叠一层 details（两级折叠，最深 2 次点击） | 最后一个折叠组，头部摘要写「4 个不可撤销操作」，**红色文字**提示 |

### 12.5 优缺点与推荐

| | 优点 | 缺点 |
| --- | --- | --- |
| ① 卡片流 | 零学习成本；所有东西都在眼前，**不存在"东西藏在哪"的问题**；搜索/向导/页签全不需要 | 桌面 1.10 屏（要滚 0.2~1 屏才能看到后面的卡）；手机 2.03 屏，探测地址在最底部；卡多时首屏信息密度低 |
| ② 折叠 | 桌面 0.77 屏、手机 1.13 屏，**信息密度与可发现性平衡最好**；摘要行替用户回答"这组现在是什么值"（冷却 5h/5min、订阅 2 条…）；锚点让跳转 1 步到位 | 两级折叠最深要点 2 次；折叠组内滚到底才知道下面还有什么；默认展开哪一组需要拍板（本版默认「节点从哪来」） |
| ③ 双栏 | 点击最少（改密钥 1 步）、页高最稳（1.00 屏）；**最适合未来继续加组**（加一个组只加一行导航）；手机退化为横向分组条，不爆版 | 8 控件的规模下右侧**大片空白**（内容 0.33 屏），显得空；左导航占 208 px，1440 下有效内容宽只剩 ~960 px；"每个组只有一两个控件"时导航的收益最低 |

**推荐：② 单页 + 分组折叠（桌面）/ 同一套在手机上也成立。**
理由（按权重）：
1. 用户否掉三页签的实质原因是「**分页格式不行**」——② 不换页，折叠本身就是"选择看哪组"的最轻形式；
2. 8 控件的真实规模下，① 的滚动成本已经出现（手机上查探测地址要滚 2 屏），③ 的导航成本又高于折叠（左侧常驻占宽 + 内容区空）；
3. ② 的摘要行解决了①③都没解决的一件事：**不展开也知道当前值**（「冷却 5h / 5min · 最多换 5 次 · 体检 15min」「订阅 2 条 · Webshare 3 条」）——这正好对应"设置页是排障时来看一眼"的真实用法；
4. ② 只有一个默认展开的策略要拍板，落地后无需再改结构。

**次选 ①**：如果用户希望"打开就看到全部"（不想有任何折叠动作），① 是唯一零点击方案，代价是滚动。
**不推荐 ③**：8 控件撑不起双栏，空白太多；但**如果将来组数涨到 8~10 组**（比如自动路由上线后再加 3 组），③ 会反超②——到时可再提。
