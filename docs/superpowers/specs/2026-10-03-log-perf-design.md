## 一、问题与基线

概览页打开一次约 **5.2 秒**（对抗代理机器 7.3 秒；雷达端到端 HTTP 实测 5.98–6.20 秒）。

一次交互触发 **3 趟**全文件扫描：

| # | 触发点 | 请求 |
| --- | --- | --- |
| 1 | `main.go:6897` `modelStatsFromCallLog` | `/api/stats?range=X` 的前半 |
| 2 | `main.go:6898` `trendsByModelFromCallLog` | 同一请求的后半 |
| 3 | `static/admin.html:900` `loadHeatmap()` | `/api/stats/trends?range=180d`，**无条件** |

第 3 趟挂在 `loadStats()` 末尾，而 `admin.html:817` 有 `setInterval(loadStats, ms)`
自动刷新——**开 10s 档就是每 10 秒烧一次三趟**。

### 成本分解（实测）

```
json.Unmarshal      2,060 ms   95.0%   ← 11.06 µs/行
time.Parse(RFC3339)    33 ms    1.9%
strings.Split          19 ms    1.1%
string(data) 拷贝       18 ms    1.0%
os.ReadFile            65 ms    3.7%
```

**I/O 层全部加起来只有 4.7%。** 任何针对 I/O 的优化（mmap、page cache、只读字节区间）
上限就是 4.7%——这是否决 mmap 方案的依据。

## 三、架构

分三部分，彼此独立，可分别回滚。

### 3.1 逐【时】聚合桶 + 尾部增量（核心）

> **自查修正**：初稿写的是「逐日桶」。**这是错的**——`trendBuckets("today")` 返回的是
> **24 个小时桶**（`calllog.go` 的 `default` 分支），日桶无法还原小时粒度。
> 雷达原型正是栽在这里：它用 `daySet[d]` 收 `"2026-10-03T10:00"`，
> 而查桶时取 `k[:10]` 得到 `"2026-10-03"`，匹配必然失败。
> 实测其原型 `range=today` 仍耗时 1.9 s——**那个 3 ms 是 30d 的数字**。
>
> 改为**小时桶**即可同时服务两类窗口：
> `today` 直接查 24 个小时桶；`7d/30d/180d` 每天的 24 个小时桶求和。
>
> **代价为零**：实测真实数据非空 (小时,模型) 桶 **673 个**，与日桶数量相同。

**核心洞察**：小时桶边界对齐整点，所以**绝大多数桶当小时结束后不再变化**。
但**「当小时结束即永久不变」这个说法不成立**——实测 **610 条记录落进了已经结束的小时桶**，
最大回退 2,801 秒（46 分 41 秒）。占比虽小（0.33%），但足以让「桶不可变」成为错误前提，
`+=` 是唯一安全写法（§4.3）。
且**写日志的就是本进程**（`callLog.append`），尾部数据它自己就知道。

```
类型：
  type hourModelAgg struct {
      N, OK, Fail int64
      PT, CT, CC, CR int64          // prompt / completion / cache_creation / cache_read
      SpeedSum float64; SpeedN int64
      TTFT  Sum float64; TTFTN  int64
  }
  // 键用本地时区归一，见 §4.2 / §4.3
  var hourBuckets map[string]*hourModelAgg // key = "2026-10-03T10|deepseek-v4-flash-free"
  var parsedTo    int64                    // 已吸收到的字节偏移
  var parsedInode uint64                   // 检测日志文件被替换
```

#### 🔴 前提：backfill 必须用【手写扫描器】，不能用 `encoding/json`

**本节所有性能数字都建立在扫描器之上，而初稿完全没提它。**实测（100.4 MB，best-of-3）：

| backfill 实现 | 耗时 | 满足「重启后首次 <350ms」？ |
| --- | --- | --- |
| `encoding/json`（现有 `CallRecord`） | **1,628 ms** | ❌ 差 4.6 倍 |
| `json.Decoder` 流式 | 1,519 ms | ❌ |
| 手写扫描器 | 331 ms | ✅ |

**照初稿写（沿用本仓库既有 `encoding/json` 风格）的实现者，验收 #4 直接失败 4.6 倍**，
且这约 180 行成本不在初稿任何一行估算里。

**扫描器承担三条正确性责任**：
1. `output_speed` 必须委托 `strconv.ParseFloat`。手写 atof 实测 **7,166/186,212（3.85%）条解析错误**
   （`65.7329268194411` vs `65.73292681944112`）。委托成本仅 +9%（331→360 ms）。
2. **时间戳整个交给 `time.Parse(time.RFC3339)`**，扫描器只切出原始 ts 字节。成本 +43 ms
   （174→217 ms），仍在预算内。这样代码里**不存在**可被后人「优化掉」的偏移判断。
   ⚠️ **禁止复制 `/tmp/radar/exp2.go:224-268` 的 `parseTS`**——它正是 §4.2 警告的手写偏移逻辑，
   且其自身注释承认已被打错过一次。**它是本轮最可能被复制粘贴的代码。**
3. **跳过 `events`/`nodes`/`node_names` 数组必须做字符串感知的深度跟踪**（约 +15 行）。
   朴素括号深度在遇到**游离 `]`** 时会静默损坏该行的全部统计且不报错。
   实测生产数据侥幸安全——17,624 个字符串内括号全部配对（如 `[DONE]`、IPv6 `[2406::1]`），
   但**任何未来一条含游离 `]` 的错误消息就会让该记录的 token 凭空消失**。

**另注**：整文件最大行 **4,193 B > 4,096 B 页**，单条记录可跨页，撕裂读无法从理论上排除。

#### 🔴 backfill 必须惰性 + single-flight

```
main.go:7013  initCallLog()
main.go:7101  ListenAndServe()      ← 在其后
```

- **绝不能把 backfill 写进 `initCallLog`**，否则直接违反「启动 <50ms」。
- 放后台 goroutine 则**backfill 期间的查询会读到半桶、返回静默错误的数字**——
  §5 原先没有这一行。
- **必须 single-flight**：§3.3 让两个请求并发，而 `/api/stats?range=` 与
  `/api/stats/trends?range=180d` 会各自判断 `size > parsedTo` 并同时开始扫描 →
  `fatal error: concurrent map writes`（**不可 recover**）。需要 mutex + double-check，
  且第二个调用者必须**等待**而非跳过（否则返回空桶）。`setInterval(loadStats, ms)` 让该窗口持续暴露。

#### 🔴 折叠小时桶必须按时间排序遍历

Go 的 map 遍历顺序随机化。若直接 `for k, v := range hourBuckets`，
同一请求连发两次的 `avg_ttft_ms` 会不同 → 验收 #2「逐位相同」在浮点字段上不可能成立，
且任何浮点断言 flaky。**必须按小时标签排序。**

**写入侧**（首选）：在 `callLog.append()` 里直接 `incr` 到桶，查询连文件都不读。
若写入侧改动风险偏高，退化为「查询时按需增量吸收」——两者接口相同。

**增量吸收**：
```
os.Stat(path) → 若 size > parsedTo，只 ReadAt(parsedTo, size)
              → 逐行解析 incr 到桶 → parsedTo = 解析成功的最后偏移
```

实测增量成本：

| 距上次吸收 | 耗时 |
| --- | --- |
| 1 分钟 | 897 µs |
| 5 分钟 | 6.4 ms |
| 1 小时 | 61 ms |
| 24 小时 | 137 ms |

**内存**（实测，非估算）：

```
非空 (小时,模型) 桶   673 个   × 96 B =  63 KB
非空 (日,模型)   桶    84 个            ← 此前误称与小时桶「数量相同」，实为 8 倍差
稠密上界 180天×24h×17模型 = 73,440 桶     = 6.7 MB
外推一年 ≈ 4,913 桶                        = 0.4 MB
```

**桶不淘汰**：稠密上界 6.7 MB 完全可接受。淘汰反而要求按小时前缀扫 map 或建二级索引，
多约 15 行和一类 bug。

## 四、三个必须知道的陷阱

这三条都是实测踩出来的，写错**不报错、只是数字悄悄错**。

### 4.1 浮点：增量均值与 Σv/n 不等价

现有 `recordModelSpeed` 用增量均值 `avg += (v-avg)/n`。
日桶只能用 `Σv/n`，两者**数学等价但浮点不逐位相等**：

```
实测（11,540 条含 output_speed 的记录）
  相对差 1.3e-16 ~ 1.7e-15
  面板显示精度 0.1 t/s，界面完全看不出
```

**决策**：接受该差异，在响应里照常返回 `avg_*`。理由是 UI 精度远低于浮点噪声，
而强行逐位一致需要按桶顺序重放增量平均，复杂度回到 O(记录数)，与 O(1) 的目标冲突。

**「不带 range 的响应逐字节相同」这条红线不受影响**——它走的是 `tokenStats`
内存计数器，不经过日桶。

### 4.2 时间戳偏移符号在下标 23，不是 19

```
186,212 行里 185,722 行（99.74%）的 ts 形如 "2026-10-03T12:22:32.308+08:00"
只有 490 行是 "...Z"
偏移符号在第 23 个字符（下标 23）；下标 19 是小数点
```

按 `v[19]` 判偏移会把 **99.74% 的记录当 UTC**，本地日桶整整偏 8 小时，
**且不产生任何错误**。正确写法必须以 `time.Parse(time.RFC3339, s)` 为准——
它本来就正确处理两种形式，实测对拍 186,212 行：时刻不一致 0 处、归一到 Local 后日桶归属不一致 0 处。

### 4.3 记录乱序 38.6%，增量合并必须用 `+=` 而不是「新建桶」

```
逆序对 71,861/186,212 = 38.6%
回退幅度 p50=18.8s  p90=1m40s  p99=6m5s  max=46m59s
```

写日志用的是 `time.Now()`（`calllog.go:202`），不同请求完成顺序与开始顺序可以差很远。
所以增量吸收时，**新记录可能落进已存在的历史日桶**，必须 `+=`，不能「若不存在则新建并赋值」。

同理，**日桶键必须用 `t.In(time.Local)` 归一**——生产日志里 490 条 `Z`(UTC) 与
185,722 条 `+08:00` 混存（2026-08-14 进程换过 TZ）。

## 四点五、并发与边界（实现前审查追加，**三条是必须照做的**）

> 本节由独立审查补入。初稿只写了「加锁保护桶」，没有画清锁边界——
> 而这里画错的后果是**进程被 Go 直接杀掉**，不是报错。

### 4.5.1 🔴 锁边界：桶 incr 必须在 `Unlock` 之前，文件写在之后

`callLog.append()`（`calllog.go:139-160`）当前是：加锁追加内存环 → **146 行 Unlock** →
154 行才 `OpenFile` 写文件。桶 incr 必须落在 **146 行的 Unlock 之前**：

```
callLog.mu.Lock()
    records 追加
    桶 incr          ← 必须在锁内
callLog.mu.Unlock()
文件写入              ← 保持在锁外（现状如此）
```

**若桶 incr 在锁外**，并发查询读同一 map 会触发
`fatal error: concurrent map read and map write`——这是 Go 的运行时致命错误，
**`recover()` 无效，直接杀进程**。

**`callLog.mu` 需升级为 `sync.RWMutex`**，`records` / `buckets` / `parsedTo` 一并保护。

**两个必须注意的点**：
1. `loadCallLogFromFile`（`calllog.go:110-137`）**已经持有 `callLog.mu`**，
   内部若再调用任何加锁 helper 会**自死锁**。
2. `main.go:1588/1608` 的 `go saveTokenStats()` 之所以并发安全，是因为
   `json.Marshal` 产出的是**值拷贝**。桶没有这一步，不能照抄那个模式。

### 4.5.2 🔴 `parsedTo` 必须记「最后一个完整换行之后的偏移」，不能记文件大小

记文件大小有三重问题：

- **吞半行**：崩溃/短写残留的无换行尾巴会被当成已解析，下次 `ReadAt` 从其**后**开始，
  半行与下一条拼成一行 → `Unmarshal` 失败 → **该记录永久丢失**，
  且那个小时桶**静默少计、无任何报错**。
- **越界后不可恢复**：短写时 `Stat` 拿到 S、实际只写到 E<S。`parsedTo` 记 S 后，
  下次 `Stat` 得 E<S。若实现成「size<parsedTo → 无事可做」，**增量从此静默失效**；
  若实现成 spec 初稿写的「size<parsedTo → 丢全部桶重建」，**一次 ENOSPC 触发 1.9 秒全量重建**。
  两个分支都错。

**正确做法**：
```
parsedTo = 最后一个【完整换行符】之后的字节偏移
```
`parsedTo ≤ 实际字节`，`ReadAt` 永不越界；同一完整行只解析一次不重复计；
代价仅是尾部片段会被重读，而重读是幂等的。
另：`append` 应检查 `Write` 返回的 n，**短写时不推进偏移**。

### 4.5.3 🔴 `clear()` 的原子区必须覆盖到 `os.Remove`

`callLog.clear()`（`calllog.go:174-180`）当前 `records` 复位在锁内、`os.Remove` 在 179 行**锁外**。
两者之间若有查询进来，会从 `parsedTo=0` 开始把**刚被删掉的整个文件**重新吸进桶——
**被清空的趋势图立刻复活**。

**做法**：`os.Remove` 移入同一临界区；或用 generation 计数，
backfill 前记 gen、合并时 gen 变了就丢弃结果。

**关于「会不会返回混合结果」**：只要查询在**单次 RLock 内**构建出完整响应，
它就线性化在 `clear` 之前或之后，必定为纯旧值或纯新值。
混合的真实来源是「分两次加锁」或「逐桶拷到锁外」，必须避免。

### 4.5.4 零填充的模型判定规则

现有实现对窗口内出现过的每个模型输出**全部**桶（含零），
这样前端折线才不断裂（`calllog.go:502-535`）。

**规则**：判定「窗口内出现过」= 该模型的键出现在窗口的桶集合里。
**只在窗口外的桶里出现过的模型不输出**——与现状等价
（`calllog.go:467-470` 在建 model 键**之前**就把窗口外记录 `continue` 掉了）。

**两条易错点**：
- **不要复制 `dayIdx` 的边界逻辑**（`calllog.go:411-415`）。它依赖本地零点 + 24 小时除法，
  换 TZ 或遇 DST 会与「按 `k[:10]` 取日期」分叉。正确做法：对每个 distinct 桶键做一次
  `time.Parse`，再交给**既有的 `bidx()`** 判定。
- **`model == ""` 是合法键**（`calllog.go:588/600`），键形如 `...T10|`。**不要过滤空 model**。

### 4.5.5 首次 backfill 期间不会有并发 append（初稿此处前提错误）

初稿写「启动 backfill 期间会持续 append 新记录」——**这对启动场景是错的**。
所有写日志路径都由 HTTP handler 触发（`calllog.go:301/315`），
而 `ListenAndServe`（`main.go:7099-7105`）在 `initCallLog`（`main.go:7013`）**之后**才启动。
**服务起来之前没有任何请求。**

但规则仍须写死，因为**运行期**的两种场景会真的并发：
- §3.1 的退化方案「查询时按需吸收」
- §5 的 clear 后全量重建

此时：`Stat` 得 S → 读 `[parsedTo, S)` → 期间新增字节落在 S 之后。
**既没被读到、也不会漏**，因为写侧 `incr` 已计入。

**前提是 `parsedTo` 恰好等于真正解析掉的末尾**。
⚠️ **绝不能读完再 `Stat` 一次把 `parsedTo` 推到新 size**——
否则 `(S, EOF]` 区间内的记录**既被写侧 incr 又被重读，双计**。

**失效判据的优先级**：以 `parsedInode` 为主（clear 后重建文件 inode 会变），
`size < parsedTo` 只作兜底。

### 4.5.6 ⚠️ 绝不能持有写锁做 1.9 秒全量解析

backfill / 全量重建必须**锁外解析、锁内合并**（换指针或 `+=`）。
若持有写锁，**每个在途代理请求的收尾**（`callLog.append`）都会被阻塞 1.9 秒——
那比现在更糟：现在只是面板慢，改完会让**代理转发也卡**。

## 五、失效与恢复

| 情况 | 判据 | 行为 |
| --- | --- | --- |
| **显式清空** | **generation 计数器**（唯一可靠手段） | 丢弃全部小时桶，`parsedTo = 0`，gen++。下次查询全量重建 |
| 日志被外部截断/替换 | `size < parsedTo` | 同上 |
| 短写/磁盘满导致的越界 | `size < parsedTo` | 同上。**不能反过来实现**——见 §4.5.2，若「无事可做」则增量永久静默失效 |
| 日志文件不存在 | `stat` 失败 | 返回空桶，**不 panic**（沿用 `69ab7dd` 的教训：必须返回非 nil 空结构） |
| 桶数据缺失某小时 | 该小时无记录 | 返回零值桶。`trendsByModelFromCallLog` 必须**输出全部桶含零**，否则前端折线断裂 |

#### 🔴 `parsedInode` 判据在 ext4 上完全失效

初稿把 inode 变化当主判据。**实测该判据 100% 不触发**：

```
本机 /dev/sda2 ext4，连续 unlink+O_CREAT 200 次
  相邻 inode 相同 199/199     唯一 inode 1/200
```

**inode 被立即复用**。因此唯一能自动发现「文件被重建」的是
`size < parsedTo`——而 §4.5.2 担心的「一次 ENOSPC 触发 1.9 秒全量重建」因此不是理论风险，
**是常态**。

**更隐蔽的漏判**：若 `parsedTo` = 100 MB 时清空日志，随后新文件在下次查询前涨到 150 MB，
则 `size(150) > parsedTo(100)` → **不判定失效**，而旧桶里还留着已删除的 50 天数据
→ **幽灵统计**。

**结论：必须引入 generation 计数器**（进程内单调递增，`clear()` 时递增，
backfill 记录进入时的 gen，合并前比对，不一致则丢弃结果）。
`size < parsedTo` 作为兜底。**初稿的 inode 方案请直接删除。**

且 §4.5.4 已说明：**绝不能读完再 Stat 一次推进 `parsedTo`**，否则双计。

**这是本设计唯一的额外分支**，必须显式实现并测试。

| 5 | map 遍历顺序随机化 → `avg_*` 不可复现 | 折叠小时桶**必须按时间排序遍历** |
