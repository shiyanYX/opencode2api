## 七、熔断闸门的根因与修法（2026-10-15 定）

### 根因：判据与闩的触发源不匹配

| 结论 | 状态 | 证据 |
|---|---|---|
| `eligible()` 函数体只有 `return n.State == NodeAvailable`，**`now` 参数根本没用** | ✅ | proxy_node.go:257-259；`hasEligibleNode()` :785-796 |
| 闩**只**由【直连 429】拉起 | ✅ | main.go:2821 / :3114，reason=`direct_429` |
| 闩**只**由【节点池状态】解除 | ✅ | quota_halt.go:91-95 |
| ⇒ 两者错配：429 按出口 IP 分桶，「直连被限流」推不出「节点池不可用」 | ✅ | 台账 §二「429 按出口 IP 分桶」 |
| **直连被放行时成功率 35.5%（3,614/10,183）** ⇒ 闸门挡掉的是本可跑通的请求 | ✅ | 实测 |
| **不是抖动，是长时间卡住**：63 小时里 23 小时纯被挡（3,509 次） | ✅ | 实测 |
| 429 是脉冲：09-21T00 真实 429 仅 58 次而闸门拦 1,254 次（**21.6×**），T03 达 **95×** | ✅ | 实测 |

### 修法（四项）

1. **解闩权**从「节点池状态」改为「该出口自己发一次真实请求拿到 2xx」；
   判据 = `!hasEligibleNode()` **且** 直连未确认恢复
2. **滞回** K=2、间隔 ≥60s（依据：≤1h 恢复率 0.0%，单次成功不可信）
3. **改 503 + `Retry-After: 30`**（现为 429 + nil header，quota_halt.go:107）；
   30s 远小于 p10=5.6h，只削峰不宣称可服务
4. **按出口分桶**：`halted bool` → `map[egressKey]*haltState`
   （★ **更正**：不能只改 quota_halt.go —— 按出口分桶必须在 main.go:2578/2821/2884/3114
   提取身份，因为 `egressKey` 全仓库 0 命中；503+Retry-After 也在 quota_halt.go:102-110，不在 39-98 范围内）

### 上线与回滚

- **1+2+3 必须一起上**；拆开会出「判据变松但回 429」「回 503 但无滞回」的中间态，**比现状更糟**
- **4 可独立上线**
- **回滚极容易**：四项同在一个文件，签名不变、无数据迁移、无配置项
- 最坏情况 = 判据写松导致「该断不断」；缓解是解闩只能由该出口真实 2xx 触发

## 十二、建连超时的正确参数（2026-10-15 定）

### 数据来源（★ 一直都在，只是没人用）

- `connect_ok` 相对 `events[0]` 的差值**退化（差值为 0），不可用**
- ★ 但节点池**早就把探针的 `latency_ms` 存进了 `proxy_state.json`** ——
  它是 dial + 代理握手 + CONNECT + TLS + HTTP 的实测往返，
  对探测成功的节点**就是成功侧建连时间**

### 分布（强双峰）

| 口径 | n | p50 | p90 | p99 | max | 备注 |
|---|---|---|---|---|---|---|
| 直接测量（proxy_state） | 141 | 11.7s | 15.4s | **18.0s** | 18.8s | >20s **0 个** |
| 日志上界（含网关开销） | 171,823 | 3.8s | 7.6s | 28.8s | 305s | >30s 占 0.94% |

★ **强双峰**：58 个节点在 1~3s、82 个在 10~19s，中间 2.6s→9.8s **完全空白**（间隙 7,140ms）
⇒ **高峰段占池子 58%**（两个来源的线路差异，不是随机波动）

### ★ 结论：用 60 秒，不用 30 秒

| 超时值 | 误杀率 | 判断 |
|---|---|---|
| 10 秒 | **58.2%** | 绝对不能用 |
| 15 秒 | **13.5%** | 不能用 |
| 30 秒 | 0.941% | 有 1.6 倍余量，但那 58% 高峰段只差 10~19s ⇒ 上游再漂就跨界 |
| **60 秒** | **0.234%** | ★ 推荐（失败侧 135s 的病态尾部一样能砍半） |

**上线策略**：先上 60 秒 + 把 `latency_ms` 落成时间序列（零新增探针成本），
跑 2 周后按真实分位数收紧到 **p99 × 1.5**。

### 「请求剩余预算」方案：否决

- ★ **致命**：根本没有总预算可分 —— main.go 注释明写流式 SSE 可持续数分钟、
  不设 `Client.Timeout`，**分母不存在**
- 次要：`loopBudget=8`，固定 60s 只丢这一次尝试还剩 7 次；
  剩余预算被吃光则把「慢」升级成「硬失败」
- 固定值状态机更简单、失败可观测、不与流式耦合

### 实现陷阱

`proxy_node.go:727` 是**裸闭包**、没有 `net.Dialer` ⇒ **不能直接套 `Dialer{Timeout:}`**；
要用 `context.WithTimeout` 包住 `dialNode`，并验证 mihomo 在该 ctx 下能及时返回
（`mihomo.go` 零 timeout 配置）。
